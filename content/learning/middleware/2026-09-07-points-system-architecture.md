## 一句话结论

积分系统不是“账户表里的余额加减”，而是一套需要同时回答 **谁发的、何时过期、被哪次业务消费、是否重复、退款如何恢复、余额能否由历史解释** 的账户与账务系统。[1]

一个稳妥的设计顺序是：先定义业务动作和不变量，再确定账户、交易、流水、批次、批次消耗和发件箱等数据事实；把核心账务更新放在同一本地事务内，把缓存、通知、报表、排行榜等外围工作放到提交后的异步链路中。[1]

## 1. 先定义系统承诺，而不是先堆组件

原文用一个具体场景展开：平台有一千万注册用户，某用户当前有 110 积分，来自两个批次：

- `B001`：50 积分，9 月 30 日到期；
- `B002`：60 积分，12 月 31 日到期。

用户兑换商品，需要消费 80 积分；请求没有及时收到响应，客户端重试了一次，几天后订单又退款。[1]

这个场景至少提出了 5 个问题：

1. 第一次请求到底有没有成功？
2. 重试会不会再次扣减 80？
3. 80 积分具体来自哪些批次？
4. 退款应该恢复原批次，还是按新的有效期发放？
5. 缓存、消息或过期任务失败后，怎样证明最终余额仍然正确？

### 1.1 业务动作要完整

积分生命周期通常不只有“加分”和“扣分”，还包括：

- 发放；
- 消费；
- 冻结、确认扣减、取消解冻；
- 退款与冲正；
- 分批过期；
- 余额和明细查询；
- 对账与受控修复。

接口还要明确返回语义：是“积分已经入账”，还是“请求已经受理、结果稍后查询”？这两个承诺对应不同的同步边界和异常处理方式。[1]

### 1.2 把“高并发”变成设计输入

原文教学假设是余额查询峰值 `20,000 QPS`、积分变更峰值 `3,000 TPS`，查询多于写入。[1] 这些数字只用于推演，不是系统能力证明，不能直接当作容量规划或压测结论。[unverified]

还要看 **单账户最大并发写入**：

- 3,000 个请求均匀落在不同账户上，主要是整体吞吐问题；
- 100 个请求同时修改一个账户，主要是同一行或同一账户的热点竞争问题。

后者会直接影响行锁、乐观锁、条件更新、单账户限流和串行化策略的选择。

### 1.3 先写出不变量

系统经历重试、超时和局部故障后，至少要守住这些不变量：[1]

- 同一业务操作只能生效一次；
- 可用积分不能扣成负数；
- 每次余额变化都要留下不可随意覆盖的历史记录；
- 退款和修正必须新增记录，不能静默修改原流水；
- 当前余额最终能够由交易、流水和积分批次共同解释。

排行榜和运营报表可以延迟几秒，但余额、幂等结果和账务历史不能使用同样宽松的正确性标准。

## 2. 总体架构：核心同步完成，外围异步收敛

![积分消费与退款示例](assets/2026-09-07-points-system/01-consume-refund.png)

**图 1｜消费 80 积分、请求重试与退款恢复原批次的示例。** 配图展示了 `B001` 扣 50、`B002` 扣 30 的分摊关系；退款是否恢复原有效期，仍属于必须明确的业务规则，不能只凭图推断。[1]

原文的总体架构可以拆成 3 条链路：

### 2.1 同步账务链路

```text
业务系统
  → API 网关
  → 业务接入与规则
  → 积分账户核心
  → 关系型数据库
```

网关负责认证、限流和基础校验；接入层负责协议转换与业务规则检查；账户核心负责幂等、余额、批次和流水；关系型数据库保存权威账务事实。[1]

### 2.2 查询链路

```text
余额查询
  → 积分查询服务
  → Redis 缓存
       └─ 未命中 → 权威数据库 → 重建缓存
```

明细、报表和排行榜可以使用只读副本或异步读模型，但 **扣减、冻结等核心判断必须回到账户核心和权威数据库**。Redis 是查询加速层，不是积分账本，不能依据 Redis 余额直接完成记账。[1]

### 2.3 异步事件链路

```text
数据库事务提交
  → 发件箱事件
  → 后台发布器 / CDC
  → 消息队列
  → 报表、排行榜、通知等外围消费者
```

账户快照、交易、流水、批次和发件箱事件属于一次核心账务变更的同步事务；通知、报表、排行榜等外围工作在提交后异步更新。[1]

### 2.4 不要第一天就拆成很多微服务

图中的“接入、规则、账户、过期、对账、查询”首先是 **业务边界**，不等于必须部署为 6 个独立服务。项目早期可以使用模块化单体，先理顺数据所有权和依赖方向；以后拆分时，负责账务原子更新的账户核心也不应被切碎，更不能允许其他服务绕过接口直接改账户库。[1]

**图 2｜积分系统总体架构。** 配图可见“统一接入与同步账务链路”“查询服务与数据层”“异步事件链路”三层关系；小字模块以原图为准。

## 3. 余额之外，需要保存哪些数据

如果只有 `user_id + balance`，系统只能回答“现在有多少”，无法解释积分从哪里来、为什么减少、何时过期。原文建议至少拆成以下事实模型：[1]

| 数据对象 | 解决的问题 | 关键要求 |
|---|---|---|
| 账户快照 | 当前有多少可用、冻结积分 | 用于快速查询，与账务变更同事务更新 |
| 积分交易 | 哪次业务操作、当前处理状态 | 幂等键唯一，状态可追踪 |
| 账户流水 | 余额为何变化、变化前后是多少 | 只追加，不覆盖历史 |
| 积分批次 | 积分来源、到期时间、剩余量 | 支撑过期规则和消费顺序 |
| 批次消耗明细 | 一次消费具体用了哪些批次 | 关联消费交易与原始批次 |
| 发件箱事件 | 哪些变更需要通知其他系统 | 与核心变更同事务提交 |

这些对象不是一一对应的：一笔积分交易可能产生多条流水，也可能消耗多个批次；发件箱事件不负责记账，只记录待处理或待发送的通知。[1]

### 3.1 开头示例的落账结果

消费 80 积分后，可以形成如下关系：

```text
积分交易 T001：消费 80，处理成功
账户流水 L001：可用积分 -80，余额 110 → 30
批次消耗 A001：从 B001 消耗 50
批次消耗 A002：从 B002 消耗 30
账户快照：可用积分 30
发件箱事件 E001：points.consumed，等待通知下游
```

这几条记录分别解释：

- **交易**：这次业务操作整体是否成功；
- **流水**：总余额怎样变化；
- **批次消耗明细**：80 分具体来自哪里；
- **批次**：原始来源和有效期；
- **发件箱**：提交后还要通知谁。

退款时，系统可以根据 `A001/A002` 找回原始批次和有效期，而不是凭当前余额猜测应该退回哪里。[1]

![积分账户数据模型](assets/2026-09-07-points-system/03-data-model.png)

**图 3｜积分账户数据模型。** 配图展示账户快照、交易 `T001`、流水 `L001`、批次消耗明细、批次和发件箱事件之间的关系；图中文字较小，复习时以原图为准。

### 3.2 什么时候考虑复式记账

如果积分涉及多个发行方、商户结算或账户之间的价值转移，可以进一步采用复式记账，用相互对应的分录追踪来源和去向。但积分子账不等于企业财务总账；对单一平台、规则简单的积分系统，“账户快照 + 不可变流水 + 积分批次”通常已经足够，最终标准是余额能否被历史记录完整解释。[1]

## 4. 一笔积分消费的安全写入链路

### 4.1 第一步：先用稳定幂等键确认是否处理过

客户端超时不代表服务端一定失败。积分核心不能收到一次请求就扣一次，而要用稳定业务身份识别同一操作。原文给出的幂等键是：

```text
幂等键 = 业务方 + 业务单号 + 操作类型
```

例如“消费”“冻结”“确认扣减”“取消冻结”是不同操作，不能共用含义模糊的键。网关可以拦截明显重复流量，但最终幂等结果必须由积分核心持久化，并由数据库唯一约束守住。[1]

PostgreSQL 官方文档将唯一约束定义为：指定列或列组在表的所有行中保持唯一；添加唯一约束还会自动创建对应的唯一 B-tree 索引。[2] 这可以作为“幂等键由数据库最终兜底”的一个具体实现依据，但不同数据库的空值语义、冲突处理语法和索引细节仍需按目标数据库核对。

### 4.2 第二步：在一个本地事务里完成记账

以立即消费 80 积分为例，一次本地事务可以按如下顺序执行：[1]

```text
1. 按幂等键创建积分交易；已存在则返回原结果
2. 锁定账户，或使用版本号控制并发
3. 原子扣减可用余额，保证余额不小于 0
4. 按“较早到期优先”消耗 B001 的 50 和 B002 的 30
5. 写入两条批次消耗明细，并追加账户流水
6. 更新账户快照，写入待处理的发件箱事件
7. 提交事务并返回结果
```

行锁、乐观锁和条件更新没有统一答案，要看单账户冲突概率和压测结果。不能先读出余额，在应用层判断后再无条件覆盖；最终扣减必须由数据库并发控制保证不会超扣。[1]

“冻结 → 确认扣减／取消解冻”也不是所有消费场景都必须经过的固定步骤。一次调用就能完成的兑换可以直接扣减，只有订单之后仍可能确认或取消时，才需要显式状态机。[1]

以 PostgreSQL 官方事务文档为例，打开事务的更新在事务完成前对其他事务不可见，提交后更新同时变得可见；发生错误或主动放弃时可以使用 `ROLLBACK` 取消尚未提交的更新。[3] 具体项目仍应结合所用数据库的隔离级别、锁行为和死锁重试策略验证。

### 4.3 第三步：数据库提交后再处理缓存

本文采用的 Cache-Aside 方案是：

```text
更新数据库并提交事务
  → 删除余额缓存
  → 下次查询未命中时回源数据库并重建
```

数据库提交与 Redis 删除不是同一个事务，删除可能失败。可以在账务事务中同时写入缓存失效事件，由后台任务重试删除；若事件还要通知多个系统，或需要削峰、独立扩容，再由后台发布器发送到 MQ。MQ 不是事务发件箱的必选项，发件箱表在一定规模内也可以承担可靠任务队列的职责。[1]

缓存要设置合理的过期时间和版本号。热点缓存失效时，可以通过请求合并或短期租约限制回源线程数；回填前再次校验版本或租约，避免慢请求把旧值重新写回缓存。无论缓存怎样优化，积分扣减仍以数据库为准。[1]

### 4.4 第四步：跨系统使用事件收敛

订单完成后发积分会跨越订单系统和积分系统。常见链路是：订单系统在同一个本地事务中保存订单状态和发件箱事件，后台任务或 CDC 将已提交事件发送出去；积分系统收到事件后，以业务单号和操作类型幂等入账。[1]

事务发件箱解决的是“业务数据提交了，但事件没有一起保存下来”的双写缺口。AWS Prescriptive Guidance 也将 transactional outbox 定义为解决数据库写入与消息/事件通知之间的 dual-write 问题。[4]

但事务发件箱不等于消息天然只处理一次：发布任务可能重复投递，消息可能延迟或乱序，消费者仍需记录已处理消息并保证幂等。AWS 文档明确提醒，事件处理服务可能发送重复消息，消费方应通过跟踪已处理消息实现幂等。[4]

![一笔积分消费的完整时序](assets/2026-09-07-points-system/04-consume-sequence.png)

**图 4｜一笔积分消费的完整时序。** 配图展示首次请求、MySQL 事务、缓存删除、异步发布，以及携带同一幂等键 `K001` 重试后返回原交易结果的关系；事务边界只覆盖账务数据库，缓存与事件发布发生在提交之后。[1]

## 5. 失败、退款、过期和对账

### 5.1 请求超时：重试只能得到原来的结果

开头的消费请求虽然超时，但只要客户端携带同一个幂等键，积分核心就应查询到交易 `T001`，返回第一次处理状态，而不是再次扣减。[1]

如果第一次仍在处理中，可以：

- 返回“处理中”，让调用方稍后查询；或
- 在有限时间内等待结果，超时后仍通过查询接口确认。

不要把“没有收到响应”直接解释成“服务端没有执行”。

### 5.2 退款：新增冲正，不修改原交易

退款时创建一笔关联 `T001` 的新交易和反向流水，而不是删除或修改原流水。系统依据 `A001/A002` 找到原先消耗的批次，再按业务规则恢复积分。[1]

原批次已经过期时，究竟是立即失效、沿用原有效期，还是获得新的有效期，是必须提前约定的产品规则。技术系统要保存原始分配关系，并完整记录最终采用的规则与结果；不能由退款代码临时猜测。

### 5.3 过期：按批次处理，而不是只改总余额

过期任务应找到已到期且仍有剩余量的批次，生成稳定任务标识，并在同一事务中：

1. 减少批次剩余量；
2. 更新账户快照；
3. 追加过期流水；
4. 记录任务完成状态。

数据量大时，可按到期日期和账户范围拆分任务，由多个节点执行。调度租约负责分工和故障接管，稳定任务标识防止节点切换或重跑造成重复清零。[1]

### 5.4 对账：自动发现，不要无审计地自动改账

周期性对账至少检查三类关系：

- 账户可用/冻结余额是否与流水、批次汇总一致；
- 业务系统与积分系统能否在总量和逐笔状态上对应；
- 发件箱、消息消费和下游读模型是否存在长期未完成记录。[1]

发现差异后可以生成差错记录和工单，附上业务单号、账户、积分数和差异类型。自动发现问题不等于直接把余额改成“正确数字”：应先定位原因，再通过受控补录或冲正修复，保留完整审计链。

## 6. 数据增长后的扩展顺序

### 6.1 查询多了：缓存和读模型

Redis 可以保存余额副本、账户状态和热点汇总；历史明细、排行榜和运营报表可以异步构建读模型。读模型只是面向查询重新组织的数据，不是账务事实，不能用于决定能否扣分。[1]

热点缓存失效时，应避免大量请求同时回源；批量缓存可加入少量随机过期时间，减少集中失效。格式合法但不存在的账户可以短期缓存空结果，降低无效请求对数据库的冲击。[1]

### 6.2 核心数据多了：先归档，再决定分片

账户、交易、流水、批次、幂等记录和发件箱适合存放在支持事务与唯一约束的关系型数据库中。普通明细和报表可以走只读副本或异步读模型，但扣减判断和权威余额仍以主库事务为准。[1]

历史流水可以分区或转入低成本归档存储，但完整性、查询和恢复流程必须可验证。很多系统先做冷热分层和索引优化，并不需要立即分库分表。[1]

真正达到单库容量或写入上限时，可以按账户标识稳定路由，让一次单账户变更涉及的数据落在同一分片，继续使用本地事务。流水量很大时，可在账户分片内按时间分区或滚动表，不要只按时间把同一账户的数据打散到不同路由。[1]

分片后的幂等键也要考虑路由：如果幂等键不包含账户等路由信息，就难以依靠单库唯一约束完成全局去重。跨账户复式分录则需要同一事务边界，或引入独立账本和跨分片协调成本。[1]

### 6.3 热点账户：总容量够，不代表单点没有瓶颈

商户公共账户、活动账户或平台发行账户可能成为热点。增加应用实例不能让同一账户行无限并发写入。可选策略包括限制单账户并发、按账户顺序执行、缩短事务、将公共账户拆成多个子账户后汇总，但必须结合业务是否允许拆分来决定。[1]

## 7. 上线与演进

上线前需要同时考虑稳定性、安全、可观测性和成本：

- 按业务方、接口和账户限流；
- 远程调用设置超时，只对可重试且幂等的操作做有限重试；
- 根据下游吞吐反推连接池、消费线程和批任务并发，不能为追积压把账户数据库冲垮；
- 通过恢复演练验证备份和故障转移，并明确 RPO/RTO；
- 使用请求号、业务单号或交易号贯穿日志、指标和链路追踪；
- 监控幂等冲突、账户锁冲突、发件箱积压、消息重试、过期任务进度和对账差异；
- 对业务接入做认证、授权和防重放，高价值兑换增加风险校验；
- 人工调账需要专门权限、审批和不可随意修改的审计记录。[1]

推荐的演进顺序是：

```text
模块化单体 + 关系型数据库
  → 先把账户、交易、流水、批次闭环记对
  → 查询成为主要流量后引入缓存
  → 通知、报表拖慢主链路后异步化
  → 数据库容量真正到上限后再分片
  → 业务边界和团队规模扩大后再拆服务
  → 历史数据影响在线性能后再归档
  → 高价值权益或跨主体结算出现后加强清算、容灾和审计
```

每增加一个组件，都应能说清它解决了哪个已经出现、或至少已经量化的问题。架构图不是产品清单，而是约束、事实和故障恢复路径的表达。[1]

## 8. 面试/设计题复述模板

> 我会先定义积分系统的不变量：同一业务操作幂等、余额不能为负、流水不可变、退款新增冲正、余额可由交易和批次解释。数据上拆账户快照、积分交易、账户流水、积分批次、批次消耗明细和发件箱。一次消费在本地事务内完成幂等记录、账户并发控制、批次扣减、流水、快照和发件箱写入；提交后删除缓存并异步发布事件。超时通过同一幂等键返回原结果，退款根据批次消耗明细生成反向交易，过期按批次处理，对账只做差异发现和受控修复。系统先用模块化单体和关系型数据库，之后根据查询流量、历史数据和热点账户等真实瓶颈逐步引入缓存、读模型、异步事件、分片和服务拆分。

## 9. 勘误与边界

1. **教学 QPS/TPS 不是容量证明。** 原文明确把 `20,000 QPS` 和 `3,000 TPS` 写成设计输入；没有硬件、请求分布、数据规模、部署拓扑和压测脚本，不能据此推导系统性能。[1][unverified]
2. **唯一约束是幂等的数据库兜底，不是完整幂等方案。** 唯一键只能阻止同一业务身份重复落库；处理中状态、失败重试、结果查询、跨系统重试仍需要状态机和业务语义。PostgreSQL 官方文档只证明其唯一约束语义，具体数据库的空值和冲突处理规则要单独核对。[2]
3. **事务发件箱不是 exactly-once。** 它解决数据库更新与事件记录之间的双写缺口；发布器和消费者仍可能重复，消费端需要跟踪处理记录并保持幂等。[4]
4. **缓存不是账务事实。** Cache-Aside、缓存失效重试和版本校验改善读取路径，但扣减、冻结和退款的权威判断仍应回到核心账务事务。[1]
5. **“冻结”不是所有消费的固定步骤。** 只有业务存在后续确认或取消时，才需要冻结状态机；立即完成的兑换可以直接扣减。[1]
6. **本篇未绑定某个具体数据库、消息队列或部署规格。** 原文未给出目标数据库版本、隔离级别、锁超时策略、消息语义或容量压测结果，因此落地前必须用目标技术栈做集成测试和故障演练。

## 10. 复习速记

```text
积分系统 = 账户快照 + 交易 + 不可变流水 + 批次 + 批次消耗 + 发件箱
幂等     = 业务方 + 业务单号 + 操作类型，数据库唯一约束兜底
消费     = 锁/版本控制 → 条件扣减 → 早到期批次优先 → 流水/批次明细 → 快照/发件箱
缓存     = 数据库提交后删缓存；Redis 只做查询加速，不做权威记账
超时     = 同一幂等键查原交易，不把未知结果当成失败
退款     = 新增冲正，依据原批次消耗明细恢复
过期     = 按批次、稳定任务 ID、同事务更新快照和流水
发件箱   = 解决数据库与事件记录双写；发布/消费仍需幂等
对账     = 发现差异 → 定位原因 → 受控补录/冲正，不直接改余额
演进     = 先模块化单体记对账，再按真实瓶颈加缓存、异步、分片、拆服务
```
