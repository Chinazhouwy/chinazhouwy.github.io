# Agent 面试复盘 01：意图识别、多任务编排与故障边界

> **练习日期**：2026-10-28  
> **写作原则**：先写问题，再写当时的回答与缺口，最后写参考方案、同行常见做法、边界与可执行实验。  
> **重要说明**：题干按当日复盘主题重新整理，**不是企业面试官的逐字原话**。方案部分有不少是为了应对更复杂 Agent 场景提出的设计设想，不能误写成个人项目已上线能力。

## 01｜完整问题：你们的企康 Agent 从用户输入到工作流输出，真实执行链路是什么？

**题干**

> 你介绍的企康智能辅助平台基于意图识别分发业务工作流。请从用户发起请求开始，解释会话信息、意图分类、路由、脚本函数、MCP 工具、检索与结果返回的实际调用顺序。哪些步骤是统一的，哪些只是特定业务流程才有？如果识别错误、工具超时或回答缺少依据，分别在哪里处理？

### 当日回答与真实经验边界

当前可确认的真实工作形态是：**预定义意图 → 路由到相应的固定业务工作流**。讨论到的业务包括客户拜访、业务咨询、情景演练、闲聊等，不同工作流视场景调用脚本函数、MCP、知识检索和模型处理。它更接近企业可控的 Workflow 编排，而不是模型每一步完全自主选择操作的开放式 Agent。

**不能凭“口述中未提到”就推断生产系统没有会话、权限、超时或日志；也不能把讨论中的所有通用架构模块反向认定为已实现。**

### 参考解法：如何清楚讲述真实调用链

1. **入口**：接收用户输入和可信会话/身份上下文。
2. **分类与参数抽取**：判断属于哪个已支持意图，提取此流程需要的参数。无法确定时可澄清或回退。
3. **固定路由**：由业务规则选择既定工作流。此处的路由不等于 ReAct 的开放式规划。
4. **流程内部处理**：根据当前节点执行脚本、调用外部 MCP 服务、按需检索知识或调用模型。
5. **结果装配**：对结构化字段、来源和响应格式做适用的校验，再返回用户。
6. **可观测性（设计建议）**：通过 traceId/stepId 记录路由、工具耗时、失败类型，方便定位。

**简化时序**

~~~text
User -> API/Session -> Intent Router -> Workflow
                                  -> Script/MCP/Retrieval (按需)
                                  -> Model/Formatter (按需)
                                  -> Response
~~~

### 业内常见做法

- **固定 Workflow / Router**：针对确定性、高约束的业务流程，维护显式的工作流图、状态和分支。
- **ReAct Tool Loop**：复杂开放任务才允许模型在工具反馈后持续决策；同时增加终止、预算、权限与审计。
- **混合式**：先选择既定工作流，在某些节点内使用受限的 Tool Loop。

### 方案的完整性与局限

单靠这条主链路还不能回答故障处理、权限注入来源、评测和质量保障。面试时应分别标记：“真实系统的实际实现”与“若由我设计，会补充的机制”。不要为了表现资深而声称目前已经具备自主规划、全局调度或故障续跑。

## 02｜完整问题：意图置信度低、两个意图很接近、识别不到时怎么办？

**题干**

> 你说前面有意图识别。如果用户输入含糊，第一、第二个候选意图差距很小，或请求不属于任何预定义意图，系统如何处理？使用大模型还是小模型做意图分类？怎样评估路由是否可靠？能否把一个分类分数直接当作“概率”？

### 当日回答与真实经验边界

讨论过“根据前两名分数差和阈值选择澄清或路由”的思路，但**它是优化设想，不是已经在线上部署的机制**。生产流程并没有被确认采用模型置信度阈值路由；也不能宣称实际存在固定的 0.8 门槛。

### 参考解法

1. 先限定已支持的意图集合，并定义“其他/无法判断”，避免把所有输入强行塞到某一个业务类别。
2. 分类结果输出意图、结构化参数与必要解释；检查必填字段。参数缺失时先澄清。
3. 对模糊或高影响路由采用保守回退：追问、展示候选流程让用户选、或转人工/通用问答。
4. 如果使用分类分数，先在真实标注数据上评估校准性；分数差阈值只能用实验确定，不能把模型自报的 confidence 天然当成概率。
5. 建立 **混淆矩阵、逐类 Precision/Recall、误路由率、弃答/澄清率、成本和延迟** 评测。重点观察业务高风险类别。
6. 实施层面保留路由 trace，记录实际选择、纠正和后续失败；在不泄露敏感内容前提下用于迭代。

### 业内常见做法

| 做法 | 优点 | 限制 |
|---|---|---|
| 规则/关键词 + 业务字段 | 可解释、成本低 | 语义覆盖有限 |
| 小分类模型 | 低延迟、吞吐高 | 长尾表达与领域迁移需评测 |
| LLM 结构化分类 | 灵活、易扩展 | 非确定性、成本与延迟、分数未必可信 |
| 规则 + 模型 + 澄清 | 可分层控制风险 | 需要样本与治理流程 |

**方案判断**：并不存在“越复杂越好”的统一答案；线上优先选择能用真实数据证明误路由风险可接受的方案。

### 动手验证

准备 50～100 条人工标注样本，故意包含多义句、不完整参数、无关请求，比较规则、小模型和 LLM 路由结果，记录澄清率和错路由率。不要只测正常样例。

## 03｜完整问题：一个用户请求包含多个意图，如何拆任务、编排串行或并行，并聚合输出？

**题干**

> 用户说：“帮我查询客户资料，找相似案例，并生成拜访建议，还要整理待办。”如果识别出多个意图，你是执行多个工作流，还是先选一个？哪些步骤可以并行、哪些必须等上一步结果？如果两个分支都修改同一个 State 会怎样？最后如何保证聚合结果可追踪？

### 当日回答与真实经验边界

这是从真实**固定意图工作流**延伸出的架构题。多任务 DAG、跨流程并发调度与自动重规划都属于**讨论的设计方案**，不能直接表述为企康系统已经落地。

### 参考解法

- **先拆出任务及依赖关系**：客户信息检索、案例查询、建议生成、待办抽取分别建 Task 节点；明确输入和产物。
- **按依赖决定执行顺序**：客户信息和案例检索可在授权范围内并发；建议生成需要等待相关检索；待办提取是否依赖结果取决于业务。
- **每个分支独立产出**：不要多个线程直接共享可变 HashMap；使用不可变结果对象或按命名空间归并 State。
- **聚合约定**：结果带 taskId、来源、状态及错误详情；部分成功时不要拼成“全部成功”的自然语言。
- **预算与取消**：总超时、每工具超时、并发上限、取消传播与重试范围需要明确。

~~~text
                  -> 客户资料查询 ----
用户任务 -> 任务拆分                  -> 建议生成 -> 聚合
                  -> 成功案例检索 ----
                  -> 待办抽取 -----------------------^
~~~

### 业内常见做法

1. **固定 DAG / Graph**：适合可预期依赖和合规业务场景。
2. **Planner → Executor**：让模型提出计划，Java 运行时校验依赖与权限，再执行；计划不应被直接当作可信代码。
3. **ReAct 逐轮决策**：对于下一步不可预知的探索性任务更自然，但更难保证预算和稳定性。

### 方案的局限

并行不是默认更快：工具可能受共享 API 限流、数据库锁、上下文争用限制，聚合也可能等待最慢分支；要通过实际压测权衡并发数。复杂分支失败需要明确“整体失败、降级还是部分结果返回”，不能一概而论。

### Java 实验

手写 3 个 Task 节点与依赖关系，分别用 CompletableFuture 或 Reactor 实现并发/串行；故意让一个分支超时、一个返回错误，观察聚合语义和 State 冲突。

## 04｜完整问题：多个子任务执行时，超时、局部失败、重试、取消和幂等如何设计？

**题干**

> 假设多任务流程有三个外部工具，其中第二个超时，第三个已成功写入外部系统。是整体重试还是只重试第二个？如果用户中途取消怎么办？如果网络超时但第三方已经成功，怎样避免重试产生第二次副作用？怎样定义“任务最终成功”？

### 参考解法

1. 按错误类别处理：瞬时网络故障允许有限重试；鉴权/参数错误通常不应原样重试；模型可纠正的工具错误可以进入下一轮推理。
2. **只重试可重试的失败节点**，前提是依赖输入未变且外部操作具备幂等或结果核对能力。
3. 为有副作用的操作生成稳定的 **operationId / idempotencyKey**，与 taskId、参数摘要绑定。
4. 给任务设置状态机，例如 PENDING → RUNNING → SUCCEEDED/FAILED/UNKNOWN/WAITING_APPROVAL；超时不等于外部必然失败。
5. 取消要区分“尚未执行的可取消任务”和“已提交外部副作用的任务”；后者可能只能补偿、查询或人工处理。
6. 聚合结果使用明确状态：ALL_SUCCEEDED、PARTIAL_SUCCEEDED、FAILED 等，避免掩盖局部失败。

### 业内常见做法

- **重试 + 指数退避 + 抖动**：适合短暂性失败，但应有限次、加预算。
- **状态机 / Saga 补偿**：适合有复杂副作用的分布式步骤；补偿动作不等于无损回滚。
- **幂等键 / 业务唯一键 / 对账查询**：针对“请求已生效但响应丢失”的不确定性。
- **死信/人工处理**：无法自动判定最终外部结果时比盲目重试更安全。

**局限**：Event Log 或 Checkpoint 只能恢复本地记录，不能凭空获知第三方已发生但未回写的事实；这与第二天的长任务恢复题直接关联。

## 05｜完整问题：Graph State、Checkpoint、Session Log、Trace 分别解决什么？能否依靠日志恢复？

**题干**

> 当 Agent 或工作流运行到一半进程崩溃，恢复时要读取什么？State 保存哪些业务值，Checkpoint 在什么时机产生，Event/Session Log 保存什么，Trace 是不是同一种东西？如果工具执行成功、状态落盘前崩溃，恢复会不会重复执行？

### 参考解法

| 机制 | 核心职责 | 不能保证什么 |
|---|---|---|
| State | 当前工作流可用的数据和执行进度 | 不等于天然持久 |
| Checkpoint | 特定边界的一致状态快照 | 不保证外部工具仅执行一次 |
| Event / Session Log | 记录状态变化、消息和工具活动，可用于重放 | 日志缺失时不能推导外部真实结果 |
| Trace | 观察调用链、耗时、异常和工具参数摘要 | 默认不是业务恢复协议 |
| Tool Operation Ledger | 记录外部操作、幂等键、状态和核验结果 | 仍依赖第三方查询或幂等能力 |

**恢复设计**：持久化任务状态与工具操作记录；可用最近 Checkpoint 加后续事件恢复进度；对未知状态的外部调用先核实或安全重试。

### 业内参考及边界

LangGraph 官方对 State、节点边界、Checkpointer 和持久执行有完整论述；对有副作用的操作，节点粒度与重放边界设计尤为关键。它是框架机制参考，不等于用户现有 Java 项目的实际实现。

- 官方：<https://docs.langchain.com/oss/javascript/langgraph/thinking-in-langgraph>
- 延伸阅读：<https://docs.langchain.com/oss/python/langgraph/add-memory>

### 动手验证

在 mini-harness 中分别模拟：① 模型结果未持久化前崩溃；② 工具调用请求已落盘但尚未执行；③ 第三方已执行但成功结果未落盘。比较三种恢复行为，记录哪些可以自动恢复、哪些必须检查外部状态。

## 06｜完整问题：如何评估多工作流 Agent，而不是只看最终回答“像不像正确”？

**题干**

> 如果意图识别准确率高，但工具调用顺序经常出错，或者用户得到的回答流畅却引用了错误的资料，你如何定位问题？需要记录哪些中间数据，怎样设计回归用例？

### 参考解法

分层而不是只做一次最终评分：

1. **Router**：逐类准确率、未知意图拒识率、关键字段抽取正确率。
2. **Orchestration**：依赖顺序、重复执行、超时与局部失败语义是否符合预期。
3. **Tools**：调用是否授权、参数是否合法、返回值和副作用是否一致。
4. **Retrieval / RAG**：权限内召回、引用匹配度、重要证据是否缺失。
5. **Final Answer**：事实依据、业务字段、结构化格式、拒答/澄清是否合理。
6. **运行质量**：端到端延迟、Token、工具成本、Trace 和人工纠正率。

参考行业做法是 **任务集 + 规则断言 + 必要的人工/模型辅助评估 + 可重放轨迹**。模型打分只能作为辅助，不能替代工具执行结果和业务断言。

**不足**：本次练习没有提供真实生产监控数据或现成评测集，以上属于可实施的评测设计，不应声称已拿到上述指标。

## 当日结论：要练的不是名词，而是边界

今天真正暴露的是几组需要明确分开的概念：

- **业务固定 Workflow 与开放式 ReAct Agent**：企康已有的内容主要是前者，后者属于下一阶段源码学习/手写实验。
- **意图分数与可靠置信度**：没有标注数据和校准，分数不是概率。
- **多意图与多任务执行**：分类不自动解决任务依赖、资源争用和聚合。
- **Checkpoint 与外部副作用幂等**：是两个不同的工程问题。
