# 从意图识别到多工作流：一次 Java 工程师的 Agent 架构复盘

> 写于 2026-10-28｜性质：**真实项目经验 + 个人推演 + 官方文档核对**。本文不是宣称所有方案均已在生产环境实现的项目总结。
>
> 写作目的：把一次面试中零散的问答变成可复盘的工程思考。**「实际参与」「个人推演」「官方能力」「待验证」必须明确分开。** 文中使用抽象业务例子，避免披露真实客户信息、接口和内部配置。

## 0. 我今天到底想明白了什么？

一开始只想回答「你们 Agent 怎么识别用户意图」，却发现这背后是一条完整的问题链：

**意图识别 → 意图不确定/多个意图 → 任务拆解 → 串行/并行 → 状态汇合 → RAG、MCP 与 LLM 汇总 → 证据评分 → 局部失败与超时 → 可恢复执行 → Trace 与评测。**

我过去做了很多 Java 业务系统，因此自然会联想到线程池、分布式事务、幂等、锁、日志、人工审核。但**可以类比，不代表它们是同一个问题**：图的 State 合并与数据库并发写入是不同层次；检索相关性与答案真实性也是不同维度。

这篇笔记的原则是：不为了面试把调研过的设计讲成自己上线过的功能。

## 1. 证据边界：我真实做过什么，哪些还只是想法？

| 判断对象 | 归类 | 能说到什么程度 |
| --- | --- | --- |
| 在企业内部 Agent 平台上通过预定义意图路由至不同业务流程 | **实际参与** | 可说明业务流程和自己负责的节点、脚本与接口接入 |
| 意图由模型根据提示词分类，并返回结构化标签 | **实际参与** | 已确认主要使用模型分类，而非独立分类模型 |
| 使用模型返回的「置信度」决定实际路由 | **没有实施的证据** | 目前**不依赖置信度阈值决策**；不能说生产使用 0.8 |
| 比较第一、第二候选意图分差 | **个人推演** | 是讨论过的改进思路，非已落地能力 |
| RAG 文档检索、外部工具/MCP 结果汇总成上下文后由 LLM 生成回答 | **据参与经历描述** | 可解释链路，但具体分支、调用先后需按真实代码核对 |
| 使用 BGE 类模型对引用、问题/答案的关联程度再筛选 | **有参与印象，细节待核实** | 要核对模型版本、输入对、分数含义和先后顺序 |
| 多意图识别、多个 Workflow 同时运行 | **个人推演** | LangGraph 支持此类编排，但不应讲成已上线 |
| Workflow 的 Retry、Checkpoint、HITL、Trace | **官方可支持或建议设计** | 是否被公司平台开放、如何配置，未确认 |
| 标准问答回归评测和人工审核 | **对实际流程的了解** | 具体指标、样本量和自动评测逻辑待核实 |

**面试表达的基本句式**：「我们目前实现了 X；它的限制是 Y；如果由我改进，我会先验证 Z，再选择方案 A/B，而不是直接上复杂框架。」

## 2. 主链路：现有实现如何描述才准确？

```text
用户输入/历史上下文（是否使用及取用范围依实际系统为准）
    ↓
模型意图识别（预定义：信息查询 / 拜访建议 / 业务咨询 / 情景演练 / 兜底）
    ↓
读取分类标签 → 对应的预定义 Workflow
    ↓
脚本函数 / 业务接口与 MCP / RAG（依场景组合）
    ↓
结果组织成提示词 → LLM 汇总答复与引用
    ↓
部分场景存在相关性筛选/评分（BGE 具体用途待核实）
    ↓
最终输出
```

它更接近 **Workflow-based Agent / LLM Router**。流程的大方向由工程代码或可视化编排提前决定，不是一个完全由模型实时规划的自主 Agent。使用了 LLM、工具和 RAG，也不自动意味着采用 ReAct 或 Plan-Execute。

### 90 秒内的原始项目答法（不能夸大）

> 我参与的是集团统一 Agent 平台上的业务应用编排，而非平台底层 Runtime 开发。入口使用提示词定义几个固定的意图，让模型以结构化格式返回意图标签，业务侧基于标签分发到对应工作流。各工作流通过脚本、已有系统接口/MCP、知识库检索等取得信息，随后把检索结果、工具数据以及问题汇总给大模型组织回答。部分场景有额外的参考资料相关性筛选。这个方案的优势是业务路径明确、便于治理；局限是对模糊、多意图和错误路由的处理能力有限。我目前没有把置信度阈值、动态多任务、Checkpoint 等说成自己已经实现的功能，这些是后续可以优化和验证的方向。

## 3. 意图识别：模型生成的「置信度」能信多少？

**结论：不应把模型自评数值直接当作经过校准的正确概率。** 大模型可以被要求输出意图和一个分数，但「0.9」并不必然代表 90% 正确率。独立分类器的 softmax 也不天然等于校准概率。

我今天最初提出「比较前两名分数」作为可能的优化思路，后来明确：**生产上并没有采用这种分差判断**。要承认这个事实。

三个反例：

1. 第一名 0.95、第二名 0.92：可能是模糊，也可能**两个任务都需要做**。
2. 第一名 0.88、第二名 0.10：差距很大，但**第一名仍可能是错误标签**。
3. 系统未支持的请求被强制选成第一名 0.95：差距再大，也不代表它落在允许的业务范围里。

### 如果要改善，优先做什么？

- 先区分：**单意图清晰**、**信息不足导致歧义**、**真实多意图**、**超出系统能力（OOS）**。不要将后三种混成低分请求。
- 收集真实且脱敏的请求，由熟悉业务的人标注；覆盖对话上下文、口语、重述、未知意图和多意图。
- 分别检查混淆矩阵、各类 Precision/Recall、OOS 召回、自动路由覆盖率、**自动执行错误率**。
- 通过离线验证测试是否有必要引入绝对阈值、Top-2 margin、二次分类、规则检查和用户澄清。
- 若某类操作影响权限或不可逆数据，**业务授权和人工审批不能靠意图分数替代**。

**所谓 0.8 阈值不是标准答案。** 即使模型分数在 0–1，也要验证其可分性和校准程度；应结合错误路由成本、覆盖率和澄清负担选择阈值。低分不必一概失败，高分也不能跳过必要的安全控制。

## 4. 多意图怎么处理：并不是所有两条 Workflow 都该并行

需要先做**任务拆解**和**依赖识别**，而不是把 Top-2 意图无脑同时执行。

| 请求示例 | 问题性质 | 合适的做法 |
| --- | --- | --- |
|「查一下 A 公司，再根据资料给出拜访建议」| B 依赖 A 的查询结果 | **先 A 后 B**，必要时并行检索 A 所需的多个信息源 |
|「分别查询 A、B 两家公司的资料」| 两个独立任务 | **并行 A/B**，结束后聚合 |
|「介绍一下 A 公司」| 意图和输出形态不清 | 尽量利用会话上下文；必要时澄清 |
|「查 A 公司，再帮我确认客户数据修改」| 包含有副作用的步骤 | 读流程与写流程隔离，鉴权并适时 HITL |

LangGraph 支持分支并行、动态 `Send`、Reducer，以及把一个图作为另一个图的子图。但集团的**上层可视化平台是否支持这些能力需要单独确认**，不能由底层是 LangGraph 推断出来。官方依据：[Graph API](https://docs.langchain.com/oss/python/langgraph/graph-api)、[Subgraphs](https://docs.langchain.com/oss/python/langgraph/use-subgraphs)。

**静态 Workflow 与 Plan-Execute 不是高低级关系。** 对固定流程、可审计、失败代价较高的业务，静态编排经常更经济；Plan-Execute 更适合目标复杂、步骤难以预先穷举、执行中可能重新规划的任务。ReAct 同样不是编码 Agent 专用。

## 5. 共享 State：我熟悉的 Java 并发问题，哪些能直接类比？

需要区分三层：

1. **Graph State 合并**：并行节点同时产出 `results`、`messages` 时，需要定义合并规则（如 Reducer），最好按 taskId 保存结果，不能靠完成顺序。它不是简单的 `synchronized` 问题。
2. **数据库与下游服务修改**：如果多个任务修改同一订单、客户信息、业务状态，仍需版本号、条件更新、唯一键、事务或幂等机制；Reducer 不能代替数据库一致性。
3. **需要人确认的业务操作**：例如数据修改、审批或真实副作用，可能在工具执行前先做 HITL。不是所有读取、所有状态变化都要人工确认；是否批准取决于风险与业务规则。

官方参考：[LangGraph State / Reducers](https://docs.langchain.com/oss/python/langgraph/graph-api)、[Interrupts / HITL](https://docs.langchain.com/oss/python/langgraph/interrupts)。

## 6. RAG + MCP + LLM：多个结果聚合、相互矛盾怎么办？

我记得实际项目中存在把 RAG 和业务接口结果拼接后交给一个 LLM 整合答案、附带参考资料的环节。但这并不意味着「大模型汇总一下」就能解决证据冲突。

**个人建议的稳妥方案：**

- 每份数据保留 `sourceId`、`retrievedAt`、来源类型、授权范围、内容摘要、可核验引用。
- **结构化业务事实优先使用有权限的权威业务接口**；RAG 文档负责制度、背景与解释，不让过期文档覆盖实时保单状态。此为建议优先级，具体业务应定义数据权威来源。
- 对互相矛盾的证据明确比较**时效、版本、适用范围和权威性**；仍无法解决则如实暴露冲突，不能要求 LLM 强行「选一个」。
- 在生成时让事实对应证据片段，必要时加入基于证据的答案核验，无法支持的断言应删掉或降级表达。
- **引用筛选最好放在生成前参与证据选择，生成后也要检查引用与断言一致性。** 如果在生成答案后直接删除了某条引用，而答案依赖这条引用，就会形成“无依据的断言”。

### BGE 到底在保证什么？

BGE 包含 Embedding、Reranker 等不同模型。以 **BGE Reranker** 为例，常见用法是对「问题—文档」成对评分，衡量相关性。这与检测「答案是否被证据逻辑蕴含（groundedness/faithfulness）」不同。

**相关性高 ≠ 文档事实正确 ≠ 答案完全被文档支持。** 即使把 Reranker 分数经 sigmoid 映射到 0–1，也不能直接当作已校准的真实概率。

我记得平台还有对「问题、答案、参考资料」关联性做筛选的机制，但具体是何种 BGE 变体、输入排列、是否有第二个评估节点，仍应查日志和配置。不能说“BGE 已经证明回答没有幻觉”。

参考：[BAAI BGE Reranker 模型说明](https://huggingface.co/BAAI/bge-reranker-v2-m3)。

## 7. 并行子任务 A 两秒、B 十五秒，B 卡住了怎么办？

这道题不能只回答「给 B 一个超时」或「先等十五秒」。应该先明确**请求的总预算与业务策略**。

假设交互式请求总预算为 5 秒（仅为假设示例）：

- 同时提交 A、B；A 在第 2 秒结束，结果保留。
- B 到第 5 秒仍未完成，主编排层标为 `TIMEOUT` 并请求取消；它的底层 HTTP、JDBC、线程不一定立刻停止，要有配套的客户端超时与协作式取消。
- 如果 B 是**可选的背景补充**：可以返回 A 的结果，并明确标注 B 未完成；也可视产品需求转异步继续。
- 如果 B 是**关键证据**：不能把只含 A 的答复伪装成完整成功；要返回缺少必要信息、错误说明或异步任务状态。
- 如果执行中存在业务写入，要判定写入是否已经发生，不能把一次超时等同于“操作一定没成功”。

这涉及两个不同时间概念：**局部 timeout** 与 **全局 deadline**。对串行步骤不能简单将每个步骤都设 5 秒，然后宣称总耗时一定不超过 5 秒。

### 我会考虑的任务策略（尚未实现）

| 字段 | 示例语义 |
| --- | --- |
| `required` | 本节点失败是否使最终答复不可成立 |
| `timeout` | 单节点等待预算 |
| `deadline` | 这次请求的总期限 |
| `fallback` | 缺数据时允许使用的降级答复 |
| `retryPolicy` | 哪些错误、次数和退避方式允许重试 |
| `sideEffect` | 是否有不可逆业务写入，需要幂等/补偿 |
| `status` | PENDING / RUNNING / SUCCEEDED / FAILED / TIMED_OUT / CANCEL_REQUESTED |

这张表是一种**工程设计建议**，不是 LangGraph 自带的统一字段规范。

## 8. 重试、幂等和局部失败

我最初认为幂等应主要靠下游保证，进一步看这是**不完整**的。

- **调用方**：识别请求、生成稳定的 operationId/idempotencyKey，控制重试上限，保留已完成子任务的结果并避免无意义的重复调用。
- **下游写入方**：以唯一键、业务条件或去重记录，保证相同请求重复到达时不会重复产生副作用。
- **编排器**：区分临时故障、永久错误、业务拒绝、取消、超时；按节点定义是否继续、部分返回、补偿还是转人工。
- **补偿**不是“回滚所有步骤”的魔法；一个已经发出的短信或已触发的外部动作可能不可撤销。

缓存命中、检索失败可以有降级策略；资金或状态变更不能简单“失败就重跑”。对跨系统写入，先问清可接受的最终一致性与责任边界。

## 9. Agent 状态到底存哪里：表、Redis、Markdown，还是 Checkpoint？

我直觉上想给每位用户一个临时工作空间，记录子任务、输入、结果。这个方向可以继续拆开：

| 类型 | 保存什么 | 可能的技术选择 |
| --- | --- | --- |
| 会话状态 | 当前轮次与历史对话、必要上下文 | 会话存储、数据库、Checkpointer |
| 执行状态 | Run ID、任务依赖、步骤状态、重试和中断位置 | LangGraph Checkpoint、数据库 |
| 长期记忆 | 跨会话事实和偏好（须有权限与隐私边界） | Store、数据库、向量索引 |
| 大型产物 | 搜索报告、附件、Markdown、生成文件 | 对象存储或文件系统 + 元数据 |

**Markdown 可以用来存最终研究产物，不适合独自承担并发任务调度和一致性控制**；同样，单纯建几张表也不会自动得到图执行恢复语义。

LangGraph 的 Checkpointer 负责 thread 范围内的图状态持久化与中断恢复，Store 负责跨 thread 的数据；是否需要专门业务任务表取决于检索、报表、权限、幂等及运营要求。参考：[Persistence](https://docs.langchain.com/oss/python/langgraph/persistence)。

## 10. Trace 与评测：不要只验证最后一句话

### Trace 是什么？

可以把它理解成 Agent 的**分布式调用链追踪**：

```text
traceId / runId / conversationId
 ├─ intent-router     模型与结果、耗时、是否解析成功
 ├─ workflow-a        子任务及状态
 │  ├─ retrieval      文档 ID、检索/重排耗时
 │  └─ tool-call      toolCallId、结果状态、错误类型
 ├─ workflow-b        子任务及状态
 ├─ llm-synthesis     模型、耗时、token 使用量
 └─ evaluator         评测类型、结果、是否人工接管
```

要保留的至少包括请求/执行 ID、节点、耗时、状态、错误类型、引用 ID、模型和版本；**不要把客户隐私、保单号或完整敏感提示词无控制地写入 Trace**。OpenTelemetry 已有 GenAI 推理、工具执行和 Workflow 等语义约定（部分仍在演进），并非必须买某个专用观测平台。参考：[OpenTelemetry GenAI 规范](https://opentelemetry.io/docs/specs/semconv/gen-ai/gen-ai-spans/)。

### Agent 评测至少要分层

| 层次 | 该检查什么 | 为什么不能只用标准问答相似度 |
| --- | --- | --- |
| 意图路由 | 意图准确、OOS、多意图、澄清 | 最终答案流畅也可能是误路由 |
| 检索 | 召回、排序、证据覆盖与时效 | 答案可能恰好答对却没找到依据 |
| 工具调用 | 参数、权限、调用次数、是否真的执行成功 | “工具成功”不等于“业务完成” |
| 答案 | 正确性、引用支撑、遗漏和不确定性处理 | 文字相似并非事实正确 |
| 任务完成 | 必需步骤是否都成功、局部失败是否正确降级 | 单轮答案分数不能反映完成率 |
| 工程稳定性 | p95 延迟、超时、重试、成本、错误率 | 评测好不代表线上稳定 |

你记得公司有标准问答回归和人工审核，可以如实介绍这一层；但**不要凭此宣称已有完整的 Trace 或工具轨迹评测**。

## 11. 「业内标准答案」到底有没有？

没有一种放之四海而皆准的「Agent 生产标准架构」。可以区分：

- **官方机制可确认**：LangGraph 支持条件分支、并行节点、Reducer、子图、Checkpoint 和 Interrupt；BGE Reranker 的一般相关性打分机制；OpenTelemetry 的部分 GenAI 追踪约定。
- **工程上较稳健的原则**：先定任务依赖，再决定并行；用全局 deadline 而非无限等待；分清必需和可选结果；下游副作用须幂等；将检索相关性与事实支撑分开；评测任务轨迹而不只比较最终文本。
- **不能在缺少数据时断言最优**：置信度阈值是多少、要不要用独立分类模型、一定采用 ReAct 还是 Plan-Execute、所有 Workflow 是否统一超时、是否引入专用 Trace 服务，都必须结合业务与实验决定。

**业内更好的方案**未必是更复杂的框架，而是能用更低成本达到明确的任务质量、可靠性和合规目标。

## 12. 面试最值得说的三段话

### A. 意图识别（45秒）

> 我们的业务流程是预定义的，模型主要负责将问题映射到意图标签，随后进入对应节点。实际运行中没有依赖模型自评置信度来做阈值路由。这个方案简单、可控，但对多意图、模糊请求和未知请求有局限。如果要优化，我会先做脱敏标注数据集和离线评测，确认错误分布，再选择澄清、任务拆分或分层分类，而不是直接写死 0.8。

### B. 多任务编排（45秒）

> 对于多意图，我会先区分真正的多任务与语义模糊，再按照数据依赖生成任务关系。独立任务可以并行，存在依赖的任务串行或部分并行。LangGraph 原生支持这类分支和结果合并，但要注意共享 State 的 Reducer、任务 ID、局部失败与整体 deadline。我们现有项目主要是预定义流程，这些是我的扩展设计思路。

### C. RAG / MCP 聚合与可靠性（60秒）

> 在业务场景中，知识检索和业务接口可能分别提供背景解释与实时业务事实。我们会把获取的结果交给模型汇总生成答案，也接触到过参考资料相关性筛选。这里我认为不能把 BGE 的相关性高分等同于事实正确；若来源相互矛盾，应先明确权威数据来源、版本与时效，再决定是否给出结论。对关键数据缺失宁可说明无法确定，也不能让 LLM 补造。进一步我希望补充引用支撑评测与端到端 Trace，但这些不能算自己已经交付的功能。

## 13. 后续需要通过代码或实测回答的 12 道题

1. 是否有稳定的意图输出 Schema？异常或未知标签如何处理？
2. 模型自评分数与实际正确率有没有相关性？怎样设计测试集？
3. 单用户连续对话时意图切换怎样影响上下文？
4. 多意图任务拆分如何识别必需数据依赖，而不是直接 Top-2 并行？
5. Graph 并行 State 合并与业务数据库并发写入的区别？
6. 一个子图失败后，兄弟节点完成的结果是否可以复用？
7. 两个任务 A=2秒、B=15秒，总预算5秒时如何保证及时返回？
8. 超时后外部工具仍在运行、甚至已经修改成功，如何确认状态？
9. 同一 toolCallId 重试能否幂等？是谁对副作用负责？
10. BGE 实际使用的是哪种模型？它比较的是哪些文本对象？阈值如何产生？
11. 引用被筛掉后，怎样确保最终回答仍有证据支撑？
12. 标准答案评测之外，如何评价路由、工具轨迹、真实任务完成率？
