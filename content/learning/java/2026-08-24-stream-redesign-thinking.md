# 如果由你来实现 Stream，会怎么设计？——一次“重新发明”的思维之旅

前面几篇分别讲了 Stream 的"行为"（惰性求值、短路）、"机制"（流水线、Spliterator、并行），还对着 JDK 源码把"创建流 → 追加操作 → 触发执行"的完整过程走了一遍。这篇换个最刁钻的角度：

**把 JDK 源码忘掉，假设你是那个要实现 Stream 的设计者**——你会怎么一步步想，又会做出哪些关键的取舍？

直接读源码的人，往往只记住了"Sink 有四个方法、opWrapSink 怎么包装"，却漏掉了最重要的东西：

**每一个设计决策背后，都是设计者撞过的墙**。我们把这些墙重新撞一遍。

## 第一步：把痛点抽象成"模型"

回到没有 Stream 的时代。你想给一组元素做"过滤 + 转换 + 排序"，写出来是这样：

```java
List<String> 结果 = new ArrayList<>();
for (String s : 源数据) {
    if (s.startsWith("A")) {          // filter
        结果.add(s.toUpperCase());    // map
    }
}
Collections.sort(结果);
```

痛点很明显：**循环是"外部迭代"**——你在亲手控制循环下标，每一步都跟数据混在一起；换个业务，循环还得重写一遍。

设计者会问一个问题：**"迭代"这件事，能不能交出去？**

我不再自己写 for，而是告诉框架"你要干什么"，让框架去循环——这就是**内部迭代**：

```java
源数据.stream()
      .filter(s -> s.startsWith("A"))
      .map(String::toUpperCase)
      .sorted()
      .collect(Collectors.toList());
```

💡 这是全文最重要的一次跃迁：**把"怎么遍历"的控制权从你手里交出去**。交出去换来的是什么？是框架可以在底层做优化——惰性求值、短路、并行，全都建立在"迭代由我控制"之上。外部迭代优化不了，内部迭代才可以。

## 第二步：API 形态——"类型即状态"

现在你要设计 API 的调用形态。最顺手的当然是**链式调用**，但有个设计难点：凭什么 `filter().map()` 后面还能继续 `.filter()`，而 `.collect()` 后面就接不下去了？

设计者给出的答案很优雅：**让中间操作返回"流"，终止操作返回"结果"**。

```java
Stream<T> filter(Predicate<T> p);       // 返回流：还能继续链
<R> Stream<R> map(Function<T, R> f);    // 返回流：还能继续链
List<T> collect(Collector<T, ?, ?> c);  // 返回结果：链到此为止
```

这就是**流式接口（Fluent Interface）模式**，也叫"方法链"。但比"能链上"更重要的是它的设计表达：

- 中间操作 = 往"操作清单"里追加一条记录，返回新清单；
- 终止操作 = 宣告清单完成，开始执行。

**类型系统替你把"还能不能继续"这件事表达出来了**——写错也编译不过。这个"类型即状态"的思路，比在文档里写"此方法后不能再调用 xxx"高明一个量级。

ℹ️ 函数式接口的选型也值得学：`Predicate`（判断，返回 boolean）、`Function`（转换，一个进一个出）、`Consumer`（消费，只进不出）、`Supplier`（生产，只出不进）——四个接口覆盖了绝大多数的"回调"场景，**用最少的类型表达最多的意图**。

## 第三步：惰性——"先记账，后算账"

链式 API 有了，但如果每个操作**调用时就立即执行**，会怎样？你试想一下：

```java
源数据.stream()
      .filter(...)   // 立即执行 → 产生一个中间 List A
      .map(...)      // 立即执行 → 产生一个中间 List B
      .sorted();     // 立即执行 → 产生一个中间 List C
```

每一步都产生一个中间集合——元素被拷来拷去，迭代了 N 次，内存和时间双重爆炸。这就是"直白实现"的两大弊端：**迭代次数多、中间结果多**。

怎么破？设计者想到了一个在其他领域成熟多年的思路：**把"构建"和"执行"分开**。

- 数据库：你写的不是执行计划，SQL 是先"构建查询"再"优化执行"；
- 编译器：先把源码解析成 AST，再优化、再生成机器码；
- Stream：链式调用只是**构建操作清单**（记账），终止操作才**触发执行**（算账）。

```java
源数据.stream()
      .filter(...)     // 记一笔账，不执行
      .map(...)        // 再记一笔，不执行
      .sorted()        // 继续记账，不执行
      .collect(...);   // 好，现在一起算
```

这就是**惰性求值**。它的本质是**把"工作"推迟到"必须出结果"的那一刻**——在此之前，所有操作只是数据，不产生任何副作用。

💡 这是全文第二个值得抄走的通用思想：**把"操作描述"和"操作执行"解耦**。你的代码里凡是"多步操作 + 结果可能用不上"的场景，都可以借鉴——比如批量请求的组装、查询条件的构建，都是"先描述、后执行"。

## 第四步：怎么把一串操作"串"起来执行？

记账容易，执行难。终止操作触发后，设计者面临一个具体问题：用户可能写了 `map().filter().sorted()` 三个操作，我该怎么做，才能在"一次遍历"里把三者全部执行？

一个朴素方案：按顺序逐个执行。但这样就有个问题——**每个操作只知道自己的逻辑，不知道下游是谁**。`map` 不知道它后面还跟了个 `sorted`，更不知道结果该传给谁。

设计者给出的方案是一个**协议**：每个操作都把自己包装成一个 **Sink**，Sink 负责"处理当前元素 → 转发给下游 Sink"，下游再处理、再转发……像一条传送带：

```java
class MapSink<T, R> extends Sink<T> {
    private final Function<T, R> mapper;
    private final Sink<R> downstream;   // 下游传送带

    void accept(T u) {
        R r = mapper.apply(u);   // 1. 干自己的活
        downstream.accept(r);    // 2. 传给下游
    }
}
```

这个 [处理 → 转发] 模型，本质上是**责任链 / 装饰器模式**：每个 Sink 都是"包着下一个 Sink"的装饰器，整条链从后往前一层层包出来，执行时从前往后一层层穿过。

💡 全文第三个值得抄走的思想：**当"多个参与者按顺序处理同一个对象"时，别用"if-else 判断下一家是谁"，用"每家都持有下一家的引用"**。这就是责任链。你写中间件（过滤器、拦截器、管道）时，用的就是这个骨架。

## 第五步：两个"协议"——可停、可缓冲

光有 [处理→转发] 还不够。设计者继续撞墙：

**墙一：短路怎么实现？** 用户写了 `limit(3)`，你还在傻傻地把 100 个元素全部传给下游？必须有一种机制让链条"提前喊停"。于是 Sink 多了两个钩子：

```java
void begin(long size);              // 开工前：下游做准备
boolean cancellationRequested();    // 每处理一个前，问下游"还要吗？"
void end();                         // 收工后：下游收尾
```

- 短路操作（`limit` / `findFirst`）：在 `cancellationRequested()` 里返回"够了"，上游收到信号就 break——相当于把 for 循环里的 `break` 变成了协议；
- 有状态操作（`sorted`）：`begin` 里开一个容器，`accept` 里往容器塞元素，`end` 里排序后再一次性转发给下游——相当于把 for 循环里的"临时数组"变成了协议。

**这就是 Sink 四方法（begin / accept / end / cancellationRequested）的全部由来**：不是刻意设计的 API，而是"让链条能停、能缓冲"的最小协议。**先有需求，后有接口**——设计接口时先问自己"到底要满足哪几个协议"，比上来就画类图靠谱得多。

## 第六步：并行——"描述式设计"的红利

最后是福利时刻。因为你前面做的所有决策（内部迭代 + 操作描述化 + Sink 链），**并行几乎是白送的**：

1. 数据是"可拆分的迭代器"（Spliterator），`trySplit()` 对半拆，拆到足够小；
2. 每块任务交给一个线程，各跑各的 Sink 链；
3. 每块结果都是"可合并的"（Collector 提供 combiner），最后合并。

注意看：**并行的代码，跟串行的一模一样**——因为用户只描述了"做什么"，没说"怎么做"。串行和并行只是**执行引擎**的差异，跟业务代码无关：

```java
list.stream();          // 串行
list.parallelStream();  // 并行：同一套描述，换一个引擎
```

💡 这是全文最有价值的洞察：**一旦你采用"描述式"设计（用户描述目标，框架决定过程），"优化"和"并行"这类底层能力就自动获得了解耦空间**。反过来，如果你让用户直接写循环（过程式），就永远没有这个空间。这就是为什么"声明式优于命令式"不只是一句口号。

## 收个尾：Stream 里值得带走的 8 个设计思想

别只记 Sink 和 Spliterator，把下面这些"可迁移"的思想带走，它们能用在你自己的代码里：

| 设计思想 | Stream 里的体现 | 你能用在哪 |
|---|---|---|
| 内部迭代 | 框架循环，你给回调 | 把"遍历逻辑"收敛到一处，留出优化空间 |
| 声明式 > 命令式 | 描述做什么，不写怎么做 | 查询构建、规则引擎、批量任务描述 |
| 类型即状态 | 中间操作返回 Stream，终止返回结果 | 用返回类型约束调用顺序，编译期挡错 |
| 惰性求值 | 先记账后算账 | 延迟加载、按需计算、组装后统一执行 |
| 责任链 / 装饰器 | Sink [处理→转发] | 中间件、过滤器、管道处理 |
| 最小协议 | Sink 四方法 | 先定"要满足哪几个协议"，再设计接口 |
| 元信息驱动优化 | Spliterator characteristics 特征位 | 用数据特征（有序/大小/不可变）驱动策略选择 |
| 描述即解耦 | 串行/并行只是换引擎 | 业务与执行策略分离，能力可插拔 |

**一句话版本**：Stream 的本质，是把"集合处理"从"你写循环"升级成"你描述目标，框架管过程"——所有看起来厉害的能力（惰性、短路、并行）都是这个升级的副产品。

从 Collectors 到惰性求值，再到流水线，最后到设计架构——这个系列四篇就齐了。
