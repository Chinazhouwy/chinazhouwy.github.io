# CountDownLatch、CyclicBarrier、Semaphore：三种等待语义

> 来源：微信公众号文章（JUC 同步工具系列）
> 关联：AQS 源码解析（三者底层实现）、JD 面经"三个锁工具选型"、PDD 面经 CompletableFuture 三组合

## 点题：谁在等谁、等什么、能不能进下一轮

| 工具 | 核心问题 | 一句话定位 |
|------|---------|-----------|
| CountDownLatch | 还剩多少件事没完成？ | 等一批事件全部结束 |
| CyclicBarrier | 这一轮还有几个参与者没到？ | 固定队友在阶段点会合 |
| Semaphore | 现在还剩几个并发名额？ | 限制同时访问资源的数量 |

它们不是"同一种等待工具的三个版本"，而是**三套不同的协作模型**：完成依赖 / 阶段会合 / 容量限制。

## 1. CountDownLatch：一次性大门

倒计时门闩：`new CountDownLatch(3)`（需要 3 次"任务已结束"信号），工作线程 `countDown()`，协调线程 `await()` 等计数归零。

**角色不对称**：工作方报告结束不等待；协调方等待全员结束。countDown 的线程减完计数立刻继续。

**三个细节**：
1. 构造参数 = 完成事件次数，不严格等于线程数（一个线程可多次 countDown）
2. 多个线程都可以 await，归零后一起放行
3. **一次性**：归零后大门永久打开，不能重置

**典型场景**：启动等组件初始化、主线程等并行查询、测试等异步回调、停机等任务收尾。也可以反做"统一起跑线"（计数 1 的门闩 + 多个工作线程 await，准备完成后一次 countDown）。

**内存语义**：countDown() 前的操作，对 await() 成功返回后的线程可见。

**协调的是"事件是否发生"，不是线程身份**——完成事件来自几个线程不重要，计数按约定归零就行。

## 2. CyclicBarrier：阶段边界互相等

固定参与者彼此等待：每个参与者 `await()`，先到的等后到的，**最后一个到达后一起通过**。名字里的 Cyclic 指成功通过后自动进入下一代，可循环复用。

**角色对称**：每个参与者都完成当前阶段、都 await、都可能等别人。

**barrierAction**：构造时传入，最后到达的线程先执行汇总逻辑，再放行其他人——适合"分片计算→集中汇总→进入下一轮"。⚠️ 汇总动作要短小确定，别塞慢 SQL/远程调用，否则最后到齐的人把全队堵住。

**团队语义**：一个人掉队，整轮失败。参与者在 await 时被中断、超时或屏障被重置 → 本轮进入 **broken 状态**，其他等待者收到 `BrokenBarrierException`。这与 Latch 完全不同：门闩不会自动知道任务失败，屏障认为"有人退出，全员到齐已不可能"。

**内存语义**：参与者 await() 前的操作对屏障动作可见；屏障动作对后续通过者可见。

**参与者数量创建时固定**；动态加入/退出用 Phaser。

## 3. Semaphore：许可证控制容量

`new Semaphore(3)`：同一时刻最多 3 个任务进入受限区域。任务关系独立——A 不需要等 B 到齐，只关心有没有许可证。

**典型场景**：限制数据库并发、第三方接口并发调用、文件转换并发度、本地有限资源。

**四个细节**：
1. **许可证无线程所有权**：理论上可由别的线程归还，代码必须自己保证借还配对
2. 只限制"能进去多少"，**不保证内部数据结构线程安全**，多线程改同一集合仍需额外同步
3. 虚拟线程时代更有价值：虚拟线程可以开很多，但数据库连接/外部接口额度不会变多——用许可证围绕真正稀缺资源限流
4. **并发数限制 ≠ 速率限制**：Semaphore(10) 表示同时最多 10 个，不代表每秒 10 次；控 QPS 用令牌桶/漏桶/RateLimiter。支持批量获取 permits（借多少还多少）

**内存语义**：release() 前的操作对后续成功 acquire() 的线程可见。

## 4. 怎么选：先问"我在协调什么"

| 维度 | CountDownLatch | CyclicBarrier | Semaphore |
|------|---------------|---------------|-----------|
| 等待条件 | 计数归零 | 固定参与者全部到齐 | 有可用许可证 |
| 参与者关系 | 完成方与等待方可以不同 | 参与者彼此等待 | 每个任务独立申请名额 |
| 是否可复用 | 否 | 是 | 是 |
| 失败影响 | 不自动传播任务异常 | 当前一代可能整体 broken | 通常只影响当前申请者 |
| 典型用途 | 等一批任务结束 | 多线程分阶段计算 | 并发限流、资源池 |

**三个问题压缩**：
- 等"一批工作都做完"？→ CountDownLatch
- 等"固定队友这一轮全部到齐"？→ CyclicBarrier
- 限制"同时进去多少个任务"？→ Semaphore

**边界场景**：参与者动态注册/注销 → Phaser；要拿返回值和异常 → Future/CompletableFuture；生产者消费者传递数据 → BlockingQueue。

工具选对代码很直；选错了就会出现"拿 Semaphore 模拟任务完成""拿 CountDownLatch 硬做多轮屏障"这种越写越别扭的设计。

## ⚠️ 四个容易踩的坑

1. **countDown() 没放 finally**：任务抛异常时完成信号不执行，await 永远等不到 0。正确写法 `try { doWork(); } finally { latch.countDown(); }`；且门闩归零 ≠ 全部成功，异常和结果需单独收集
2. **屏障参与数 > 线程池线程数**：3 线程池 + 5 参与者 → 前 3 个占满线程池停在 await，后 2 个躺在队列永远没线程执行，谁也推进不了。不是 CyclicBarrier 的 bug，是执行资源和参与者数量设计错了
3. **没拿到许可证却 release()**：许可证凭空增加，限流悄悄失效。正确模式：布尔变量记录是否获取成功，只在成功后归还；反向同样危险——拿到后忘 release，许可证泄漏，最后全堵在入口
4. **只看"能阻塞线程"忽略协调语义**：三个工具不能随便互换——Latch 不是可复用阶段屏障，Barrier 不是主线程单方面等子任务的最佳工具，Semaphore 不是任务完成通知器

## 🎤 面试怎么答

**Q1：三者有什么区别？**
按"协调语义→参与者关系→复用性→典型场景"四步组织：
- CountDownLatch 一次性完成门闩：工作方 countDown 报告完成、协调方 await 等计数归零，工作方不互相等，适合主线程等一批任务结束
- CyclicBarrier 固定参与者阶段会合点：全员 await、先到等后到、到齐共同进下一阶段，可循环复用 + barrierAction，适合分阶段计算
- Semaphore 许可证计数器：acquire/release 借还名额限制并发数，任务间不需到齐、无整批等待语义

**加分回答（底层实现）**：CountDownLatch 和 Semaphore 的经典实现都基于 **AQS 共享模式**，但 state 含义不同——前者是剩余计数，后者是剩余许可证；CyclicBarrier 使用 **ReentrantLock + Condition + 代际状态** 管理每一轮屏障。

**Q2：失败语义和内存可见性？**
- Latch：不自动传播任务异常，只要都 countDown 就放行；漏 countDown 则一直阻塞
- Barrier：失败是整轮性的——中断/超时/重置/屏障动作失败 → 当前代 broken，其他等待者收到异常
- Semaphore：只影响当前申请者，但获取归还必须成对，否则泄漏或膨胀
- 内存语义：Latch = countDown 前操作对 await 返回后可见；Barrier = await 前操作对屏障动作和随后通过者可见；Semaphore = release 前操作对后续 acquire 成功者可见

面试官真正考的是：你是否只会背"一个可复用、一个不可复用"，还是理解了完整的协调契约。

## 💬 一句话总结

Latch 等事情做完，Barrier 等队友到齐，Semaphore 等名额空出；看起来都在等，等的条件完全不同。
