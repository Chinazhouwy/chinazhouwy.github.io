# 考研 408 计算机网络：TCP 可靠性，丢包后到底发生了什么

> 【本卡片解决】TCP 如何知道哪个字节到了、哪个字节没到，以及窗口变化为什么同时受到接收方和网络状态影响。

## 01｜四条线分工

| 机制 | 解决的问题 |
|---|---|
| 序号 | 数据字节如何排序、去重 |
| 确认号 | 接收方已经连续收到哪里 |
| 重传 | 数据丢失后如何补发 |
| 窗口 | 一次允许在途多少数据 |

TCP 的确认号通常表示“期望收到的下一个字节序号”。它不是简单地对每个报文段编号，题目要看的是字节流位置。

## 02｜连接建立和释放

```text
建立：SYN → SYN + ACK → ACK
释放：FIN → ACK → FIN → ACK
```

建立连接需要确认双方的初始序号和收发能力；释放连接通常分成两个方向，不能把它机械地记成一次握手。

## 03｜流量控制和拥塞控制

```text
发送窗口 = min(接收窗口 rwnd, 拥塞窗口 cwnd)
```

接收窗口反映接收方缓冲区还能接收多少；拥塞窗口反映发送方对网络承载能力的估计。一个来自接收端，一个来自网络状态，含义不同但共同限制发送速度。

慢开始阶段拥塞窗口增长较快，达到阈值后进入拥塞避免；出现超时、重复确认等不同信号时，窗口调整方式也不同。做题要先标记事件类型，再画窗口变化。

## 04｜为什么只看 ACK 不够

确认可以反映连续到达情况，重复确认可能提示中间数据缺失，但不能单独决定网络一定拥塞。还要结合超时、窗口和发送速率判断。

## 易错点

- TCP 面向字节流，UDP 数据报有消息边界。
- 流量控制保护接收方，拥塞控制保护网络。
- 三次握手不是为了“让服务器知道客户端在线”这么简单，还要同步双方序号。
- HTTP 是应用层协议，TCP 不负责解释 HTTP 请求内容。

## 一句话结论

TCP 题沿着“字节编号 → 确认 → 丢失处理 → 窗口限制”推演，看到事件再判断可靠性、流量或拥塞机制。
