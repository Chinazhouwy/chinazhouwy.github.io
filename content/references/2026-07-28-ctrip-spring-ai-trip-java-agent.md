## 一、Java 做 Agent 到底缺什么

### 现状痛点

1. **技术栈转型困难**: 国内后端团队技术栈基本以 Java 为主。用 Python 独立搭建 Agent 服务会带来跨语言 RPC 调用、需维护两套可观测体系、两套配置中心。团队要的不是"能用 Python 写 Agent"，而是"能用 Java 写、能长在现有业务代码旁"的 Agent。

2. **缺少企业级治理**: 多数开源框架只做到能跑起来——调模型、拼提示词、接工具。但安全审计、流控熔断、会话管理、权限隔离、攻击防御一片空白。

3. **运行时空白**: 即便选了 Java 方案，现有框架基本只做到能调通大模型。生产化真正难点在运行时 Runtime: 短期记忆怎么管、单次工具返回的大量结果怎么处理、产生错误结果的流程怎么回溯、工具怎么在不重启的情况下增减、并发工具调用怎么保证一致性——这些几乎没有框架给你兜底。

### 现有 Java 方案对比

| 方案 | 定位 | 局限 |
|------|------|------|
| **Spring AI** | 模型抽象层，统一不同厂商模型为 Model 接口 | 不是 Agent 运行时。ChatMemory 只有滑动窗口等基础实现；工具返回值直接进上下文、无溢出保护；可观测性靠 Micrometer 手动埋点；工具注册是启动期静态的 |
| **Spring AI Alibaba** | Graph 编排 + Nacos 集成 + Studio 可视化调试 | 重点在编排，携程已有内部配置中心 QConfig/CAT/MCP 网关替换 Nacos，且需求是让单个 Agent 更稳定运行 |
| **AgentScope Java** | 一站式开发平台，不可变消息 + A2A/MCP 双协议 + Reactor 响应式 | 适合新起项目。携程的场景是往已有 Spring Boot 应用里"粘"Agent |

Spring AI 是模型抽象层，不是 Agent 运行时。它给你一辆能和大模型对话的车，但生产化需要的变速箱、ABS、行车电脑等高级组件，得自己造。

## 二、设计哲学：四条核心原则

1. **不重造 Spring AI 已有轮子**: 所有扩展能力通过 Advisor、ToolCallback、Observation 等接口挂载，融入 Spring AI 体系。业务方可直接使用 Spring AI 原生能力，也可按需启用增强能力。

2. **审计优先**: 写入链路简单快速，原始数据零加工直接入库，支持随时复盘、审计与流程回放。所有 Agent 决策全部落库统一管理。

3. **渐进式压缩，不做断崖式截断**: 面对上下文压力，信息从原文渐进降级到高密度摘要，而不是断崖式截断，也不是被打散成检索碎片。要的是"斜坡"——保留连续的、可读的、但密度不同的会话历史。

4. **默认安全，业务无感**: 异常路径的清理、并发下的一致性、工具下线的安全窗口、进程重启后的会话续接，这些脏活都内建框架处理，业务方只需关注领域逻辑。

## 三、Spring-Ai-Trip 架构概览

核心数据流: 一次 Agent 调用穿过 Harness 的完整路径:

```
业务侧调用 agent.spawn() → Spring-AI-Trip Harness
  ↓
首次请求大模型前: 加载提示词、技能清单、MCP 快照
  ↓
核心 Agent Loop:
  ├─ MODEL STEP:   调 LLM（通过 Spring AI）
  ├─ ACTION STEP:  并行工具调用
  ├─ PAYLOAD STEP: 防止上下文溢出
  └─ NEXT TURN:    更新会话记忆、预估与摘要
  ↓
记忆系统: 持久化存储原始会话用于审计，按需执行渐进压缩
  ↓
收尾+清理: Loop 结束后上报完整 Span，Micrometer → Grafana；
           清理临时文件、会话缓存、MCP 工具引用
  ↓
可观测输出: Span+Event Tree、模型思考过程、工具入参和结果、
           token 用量、失败报错 → CAT/Grafana
```

## 四、短期记忆：三层渐进式压缩

> 记忆不是 Agent 的附加功能，而是 Agent 区别于 LLM API 的本质特征。

### 通用做法的缺陷

| 方案 | 问题 |
|------|------|
| **滑动窗口** (MessageWindowChatMemory) | 用位置作为唯一淘汰标准。用户第 1 轮说的"帮我查 ORD-2024-001 的退款"，可能在第 20 轮被窗口滑出，Agent 开始目标漂移 |
| **RAG 检索** | 能召回相关片段，但感知不到时序，拼不出对话的整体画像。Agent 需要知道用户是谁、话题是什么、任务进展到哪一步了 |

### 核心理念

**永远不丢弃任何信息；注入模型时，按信息价值的衰减曲线，渐进地压缩。**

"渐进"是关键词——信息不是在某个边界突然消失，也不是被打散成碎片，而是连续、分级地从高精度原文过渡到高密度摘要。

设计灵感来自 Claude Code 的四层上下文管理，但做了服务端适配——Claude Code 是单机 CLI、单进程持有会话状态；携程的服务端多实例、多会话并发、分布式部署，压缩逻辑必须是读取时触发而非写入时。

---

### 三层防御体系

#### 第一层：读写分离（基础）

- **写入**: 永远是简单的一次落库，毫秒级，零压缩开销
- **读取**: 所有压缩只发生在读取、注入模型的那一刻
- 原始数据一条不少地落库，复盘、审计、回放随时可得
- 附带解决服务端跨实例会话续接：任何实例拿到 sessionId，都能从库里拿到完整历史

#### 第二层：工具返回值微压缩（Claude Code AutoCompact 思路）

工具调用的返回值价值衰减极快。一个 3000 token 的查询结果，Agent 只需要告诉用户"订单已退款，已发货"这个简单事实。

```
压缩前 (约 3000 tokens):
[工具] query_order → {"status": 200, "body": {"orderId": "...", "items": [...大量数据...]}}

压缩后 (约 10 tokens):
[工具] query_order → "[旧工具结果已清理，可通过 evidence-id=e7f3a 回查]"
```

**三条规则**:
1. **以完结轮次为单位**: 工具调用链可能横跨好几条消息，只有当整轮真正结束才有资格被压缩，绝不压缩中间结果和正在进行的调用链
2. **按工具分策略**: 不同工具使用不同压缩规则，关键操作永不压缩、查询结果过期即可清理
3. **压缩带证据引用**: 替换后的文本带 evidence-id，如需回查原始数据可直接定位

#### 第三层：LLM 结构化摘要（九段式模板）

压缩后仍然超预算，才动用大模型把早期对话压缩成摘要。不是让模型随便总结，而是按固定的**九段式模板**来写，每段有优先级:

| 优先级 | 段落 | 说明 |
|--------|------|------|
| P0 | Core State（核心状态） | 当前进展、关键事实 |
| P0 | Pending Tasks（待办任务） | 未完成的任务列表 |
| P0 | User Intent（用户意图） | 用户要什么 |
| P1 | Key Decisions（关键决策） | 已做的重大决定 |
| P1 | Important Facts（重要事实） | 不可丢失的上下文 |
| P2 | Completed Work（已完成工作） | 已完成的步骤 |
| P2 | Errors And Corrections | 错误与修正 |
| P3 | Problem Solving | 问题解决思路 |
| P3 | All User Messages | 用户原始消息 |

**增量更新**: 在已有摘要基础上更新九段，而不是从头重写。摘要质量随对话深度线性提升，而不是反复推倒重来。

摘要以 `<system-reminder>` 标签包裹，作为一条历史消息注入，排在近期原文之前，既压缩了上下文，又保证会话连续性。

#### 与 AgentScope Java 的对比

AgentScope Java 的短期记忆走标准消息容器，长期记忆委托给 Mem0/阿里百炼等第三方。其重心是"记忆服务的对接"而不是"单会话内不忘事"。携程的取向往"记忆的注入形态"方向走，两种取向互补。

---

### 悬空调用修复

服务端才会踩的坑：进程重启时，模型正在执行工具调用链。重启后库里只留下了 assistant 消息（含 tool_calls），缺失对应的 tool 消息——违反大模型 API 的消息协议，下次调模型直接报错。

框架在加载历史时会自动检测并修复这种残缺，把悬空的 tool_calls 消息删除，让会话能安全地接着跑。

### 动态历史窗口配额

给历史消息分配固定配额（如总窗口的 80%）建立在错误假设上：prompt 里除历史之外的部分是稳定的。事实是——系统提示词（几十到三千多 token）、工具 Schema（20 个工具轻松过万）、当前用户输入（一句"好"是 1 token，粘贴一份日志是几千 token）都在剧烈浮动。

**正确做法**:

```
有效窗口 = 上下文窗口 - 预留输出(默认 8000) - 安全缓冲(默认 3000)
固定开销 = 系统提示词 + 工具 Schema + 当前输入
历史窗口 = 有效窗口 - 固定开销
预估总量 = 历史 tokens + 摘要 tokens + 新消息 tokens
触发压缩 = 预估总量 > 有效窗口 × 阈值(默认 0.90)
```

关键在"先扣后算"——不可压缩的模型预留输出和安全缓冲先扣掉，固定开销再扣掉，剩下的才是历史消息的真实可用空间。所有 token 数由一个本地近似估算器处理。

## 五、可观测性：Span + Event

Agent 的故障模式和传统服务根本不同——没有报错路径，没有错误码，服务运行一切正常只是推理方向偏了。APM 能看到接口耗时分布，但覆盖不到推理层：模型在哪一步、基于什么证据、做出了什么判断。

### 真实排障案例

用户问："帮我看看为什么昨天下年订单转化率跌了"。Agent 调了几个工具，最后回答："是因为超时率上升，影响了支付链路"。结论有零有整，业务方信了，排查支付链路一整天——白忙。

**根因回放**: 模型第 3 轮推理时说了句"超时率上升 = 支付链路问题"，但那个工具的监控范围其实只覆盖了一个子域。真正的因果关系在第 5 轮数据里。

有了 Span + Event 逐轮回放，一眼锁定：不是模型的锅，是那个工具的数据范围有问题——去修工具，而不是调提示词。

### 认知可观测 vs 传统监控

| 维度 | 传统监控 | 认知可观测 |
|------|----------|------------|
| 关注什么 | 服务有没有报错 | 模型基于什么证据、做出了什么推理 |
| 数据形态 | 日志行/指标点/调用链 | Agent 执行的思维链树 |
| 排障方式 | 查日志关键字 | 回放完整会话 Span+Event 树 |

### 模型设计

一次 Agent 执行被建模成一棵由 **Span** 和 **Event** 组成的树:

- **Span**: 有起点终点、可嵌套的执行区间。Agent "思考→行动→再思考"的循环链路被 Span 的嵌套特性完整还原
- **Event**: Span 内部的关键瞬间——模型的思维链、每次回复、工具的入参与出参、以及错误。Thinking 事件能显式捕获模型思考过程

### 可观测后台

前端做了一个专门服务于 Agent 排障的可视化后台。把 Agent 的每一次执行的完整上下文、每步思维链、工具入参出参、token 与耗时分布、关键事件的现场，聚合在同一个视图里。

**调优对比**: 写完一版提示词、加了一个工具、换了一个模型之后，改动到底让 Agent 变好了还是变差了——不再靠肉眼比对输出去猜，而是能落到一条条可对照的证据上。

## 六、Spill：大结果的溢出保护

短期记忆管的是随时间累积的膨胀，但还有一类膨胀是"瞬间爆炸"——一个 MCP 工具单次调用返回将近 5 万 token。

### 三个并发问题

1. **空间挤占**: 单条消息吃掉大量上下文窗口，其他历史被迫大规模压缩甚至丢失
2. **注意力稀释**: 模型淹没在海量它根本不关心的数据里
3. **重复计费**: 这份报文会跟着后续每一轮对话反复重新发送，token 一次次翻倍计费

### Spill 设计：类比虚拟内存

超过阈值（默认 32000 字符）的工具返回值，框架自动接管:
- 完整原文落盘持久化
- 给模型的上下文里只留一段预览（默认前 2048 字符）+ 一句说明 + 一个可回查的路径

```
[工具结果过大，已溢出到磁盘] 预览(前 2048 字符): {"code": 0, "data": [...]
[完整数据存储于 spill://order-assistant/conv-abc/tool-7f3a.json]
如需查看完整数据，可使用读取工具按该路径获取。
```

关键设计: **把要不要看全文的决策权交给模型**。大多数时候预览里的信息已经足够推理；真需要全文里的细节，模型可以主动拿着路径去回读。从"全部灌入大脑"变成"需要时再查"。

### 打磨的细节

- **按 tool 粒度配置**: 哪些工具需要溢出保护、阈值多少、预览策略
- **智能截取**: JSON List 类型的结果，预览时智能截取前若干项
- **范围读取**: 回读接口支持按字节区间、按 JSON Path、按分页游标读取
- **会话作用域清理**: Spill 文件按 agentName/sessionId/toolId 组织，会话结束跟着清理
- **并发一致性**: 多工具并发 Spill 时文件名不冲突、取回顺序不乱、事件挂载到各自对应的 Span

### 与其他方案对比

- **Spring AI**: 目前没有溢出保护的原生抽象，工具返回值直接塞进上下文
- **LangChain**: 调用方手动 truncate，信息直接丢了
- **AgentScope Java**: ToolResultEvictionMiddleware 实现了类似 Spill 的逻辑，并在设计文档中明确区分了 eviction（解决上下文宽度）和 compaction（解决上下文长度）

## 七、能力供给：Skill 系统 + MCP 热插拔

### 问题

Agent 运行时需要的能力不应该在启动时全部塞进上下文——工具 Schema 都塞进去，20 个工具轻松吃掉上万 token，模型真实可用的窗口严重缩水。更别提工具还会变：今天上线新数据源，明天下线旧接口。

### Skill 按需加载

**上下文里只放技能清单（name + description），真正使用时才加载完整指令。**

Spring AI 在这件事上是一片空白：要么自己拼加载器，要么把指令全塞进 system prompt。

携程做了两个来源的实现:

| 来源 | 说明 |
|------|------|
| **内置 Skill** (classpath/file) | 团队沉淀的通用能力（日志分析、数据库查询、ClickHouse 等），打包在框架 Jar 里一起发布 |
| **DB 动态 Skill** (后台灵活配置) | spawn() Agent 实例时拉取当前 (appId, agentName) 绑定的技能清单。可在后台新增、修改、绑定新技能。同名 DB Skill 覆盖内置 Skill |

### MCP 动态工具注册

工具集可由配置中心（如 QConfig）配置，支持运行时热更新——改配置立即生效，无需重启、打包发布。

**热更新的安全机制**:
1. **引用计数 + Rem**: 旧工具 MCP 连接等所有正在调用的请求都结束才真正释放——不会在请求执行到一半时把连接抽走
2. **增量更新**: 只更新配置真正变动的工具，避免整个 MCP Server 全部重连

### 内置原子工具

框架内建了一批开箱即用的原子工具: 文件读写、命令行、任务清单、HTTP 调用等。

## 八、并行工具调用：虚拟线程

模型在一轮里请求了多个独立工具（查订单、查物流、查用户等级），串行执行意味着耗时相加，用户等得不耐烦。

### 虚拟线程实现

当模型在一轮里请求多个独立工具调用，框架用 **虚拟线程（Virtual Threads）** 并发执行——总耗时从各段相加变成取最长的那段。

虚拟线程极轻量——10 万个也扛得住，完美适配工具调用这种"大部分时间在等网络"的 IO 密集场景。阻塞时会自动释放载体 OS 线程，不会因 IO 等待占满线程池。

### 并发一致性保证

- **顺序标注**: 并发工具调用的结果自动标注顺序，确保注入模型时卡片顺序和 prompt 里请求的对应，不是 200ms 级随机乱序
- **观测 Span 不串味**: 并发执行时各自的 Span 隔离，Thinking / ToolInput / ToolOutput 事件归位正确
- **Spill 文件不冲突**: 多工具并发触发 Spill 时文件命名不冲突
- **完结轮次判定**: 并发+串行混合时"完结轮次"的判定依然正确

## 九、端到端实战：一次排障会话全链路

场景: "帮我排查下为什么订单 ORD-2024-0117 支付超时？"

```
Step 1 - 技能加载:
  收到问题 → Agent 扫一眼技能清单 → 判断是支付排障
  → 用内置工具把"支付状态机排查"技能正文加载进来
  → 配置中心早已把该环境的查询工具热挂载好

Step 2 - 并行调用:
  模型一次性决定: 查订单、查支付流水、查网关回调日志
  三个调用互不依赖 → 虚拟线程并发执行 → 耗时取最长的一段

Step 3 - Spill 大报文:
  网关回调日志返回 4 万字 → 超过阈值自动 Spill
  → 模型拿预览判断关键信息不在里面 → 拿路径只回读需要的那段

Step 4 - 多轮对话不丢上下文:
  给出初步结论后用户追问"网关重试过没有""换昨天同时段再看看"
  → 新轮对话触发压缩: 前几轮完整工具返回值被微压缩
  → 更早的几轮被压缩成结构化摘要
  → "排查 ORD-2024-0117 支付超时"这个目标始终锁定在摘要 P0 段

Step 5 - 排障回放:
  整个过程被完整记录成 Span+Event 树
  → 万一结论有问题，一眼看到模型在哪步、基于什么证据想岔了

Step 6 - 会话结束清理:
  无论顺利结案还是中途被取消 → Spill 文件、内存缓存、临时工具连接成套释放
```
