## 01 · String 不可变与版本差异（Q14）【P1】

### 手册原文（解释版）

**① 不可变来自封装，而不是只写 final。** String 的逻辑字符内容在创建后不改变。类被 final 限制继承，内部存储不通过公开接口暴露为可写数组，方法也不修改已有字符串的内容。字段 final 仅限制引用重新指向其他数组，不能禁止数组元素被改。接受外部 char[] 的公开构造器做防御性复制；toCharArray() 也返回副本。内部 hash 缓存可以变化，它是派生信息，不改变逻辑内容。

**② 操作返回结果，不代表一律创建对象。** 教学例：`char[] a={'A','B'}; String s=new String(a); a[0]='X';` 此时 s 仍为 AB，因为构造时已复制。拼接出不同内容需要另一个字符串结果，但某些无变化操作可以返回 this，例如覆盖全长的 substring，以及没有命中字符的 replace。不可变约束是"旧对象内容不变"，不是"每个方法必须分配新对象"。

**③ 存储编码与字符计数要分开。** JDK 8 的主要表示为 char[]，每个 char 是一个 UTF-16 代码单元。JDK 9 起 Compact Strings 通常以 byte[] 加 coder 表示：整串能用 Latin-1 表示才使用单字节形式；否则整串使用 UTF-16 的双字节形式，不是逐字混用两种宽度。`"A😀".length()` 为 3，因为表情占一个代理对；codePointCount 为 2。`"e\u0301"` 的长度和码点数都是 2，但常显示成一个带重音的字素。

**④ 字符串池不等于一块装字符串的特殊堆。** intern 返回内容相同字符串的规范引用。应区别 class 文件中的常量池、类加载后运行时常量池，以及 HotSpot 的 StringTable。现代 HotSpot 中，String 对象及其内容数组在堆里；StringTable 是 native 层维护规范引用的表结构。

| 结构 | 作用及位置 |
|---|---|
| class 文件常量池 | .class 文件格式的一部分，保存字面量和符号引用等 |
| 运行时常量池 | 类加载后的常量信息，关联类元数据 |
| 字符串规范引用表 StringTable | HotSpot 在 native 层维护表，引用的 String 对象和内容数组在堆中 |

### 60–90 秒口述（手册版）

String 不可变靠内部数据封装和公开操作约束，final 引用本身不能冻结数组。8 主要使用 char 数组，9 起通常用 byte 数组和 coder，按整串选择 Latin-1 或 UTF-16。length 数代码单元，码点计数仍不等于可见字素。现代 HotSpot 的字符串对象在堆中，native StringTable 管理规范引用。

### 会话问答

**问 1｜"存储编码与字符计数要分开，没太理解。codePointCount、Compact Strings 以 byte[] 加 coder 表示是什么？源码看起来太复杂。"**

解答：这段话把两个互相独立的层面放在一起——**存储层**（JVM 内部用什么格式放字符串：JDK 8 是 char[]，JDK 9 起是 byte[] + coder）和**计数层**（length()/charAt() 数什么：永远是 UTF-16 代码单元，从 JDK 8 到 9 一个字没变）。混为一谈会得出"byte[] 存的串 length 应该变小了"的错误结论。源码复杂的根源：每个 String 操作都有 StringLatin1 和 StringUTF16 两份平行实现，外层按 coder 分发。记忆模型：**byte[] 是物理存储，coder 是"这块字节该怎么解释"的开关，公开 API 永远按 UTF-16 代码单元说话。**

数"字符"有三个单位：**代码单元**（一个 UTF-16 槽位，2 字节，就是 char，length()/charAt() 数它）→ **码点**（一个真实 Unicode 字符，codePointCount() 数它）→ **字素**（用户眼里的"一个字"，JDK 无直接 API）。`"A😀"`：length=3（😀 是代理对占两个单元）、码点=2；`"e\u0301"`：length 和码点都是 2，但显示成一个 é，字素只有 1。阶梯：`length() ≥ codePointCount ≥ 用户看到的字数`。

**问 2｜"UTF-16 代码单元和 UTF-8、GBK 的差别？StringLatin1 是啥编码？CompactStrings 这个 JVM 怎么传递到 String 类里的？"**

解答：Unicode 只负责给字符**编号**（码点），UTF-8 和 UTF-16 是把编号变字节序列的两种方案，GBK 是自带字符表的早期国标（非 Unicode）。

| | "A" (U+0041) | "中" (U+4E2D) | "😀" (U+1F600) |
|---|---|---|---|
| UTF-8 | 1 字节 | 3 字节 | 4 字节 |
| UTF-16 | 2 字节 | 2 字节 | 4 字节（2 单元） |
| GBK | 1 字节 | 2 字节 | 无法表示 |

"代码单元"是编码处理字节流的最小槽位：UTF-8 的单元是 1 字节，UTF-16 的单元是 2 字节。Java String 的 API 语义钉死在 UTF-16 代码单元上；UTF-8/GBK 只出现在 IO 边界（`getBytes(charset)` / `new String(bytes, charset)`），乱码的全部根源是边界两侧编码约定不一致。JDK 18 起 file.encoding 默认 UTF-8（JEP 400）。

StringLatin1 = ISO-8859-1（单字节，覆盖 U+0000–U+00FF，即 ASCII + 西欧字母）作为 String 内部存储格式时的**操作工具类**——不是新编码，同一个编码在 IO 层叫 `StandardCharsets.ISO_8859_1`。它只覆盖 256 个字符，**没有中文**，所以串里混进一个汉字就整串切 UTF-16。

CompactStrings 的传递机制（JDK 25 String.java:197-232 实测）：

```java
static final boolean COMPACT_STRINGS;
static {
    COMPACT_STRINGS = true;   // ← 只是占位！javadoc："The actual value for this field is injected by JVM."
}
```

传递链：`-XX:+/-CompactStrings` → HotSpot 解析进 flag 表（PrintFlagsFinal 显示 `pd product`，平台相关——"通常"二字的来源之一）→ VM 的 native 引导阶段**直接写进这个静态字段**。占位符写法的两个原因：① 写成 `static final boolean X = true` 常量表达式会被 javac 内联进所有引用类，运行时改 flag 对已编译类失效；② 静态块赋值避免 VM 初始化期的循环依赖。运行时性能靠 JIT 常量折叠：flag 关闭时 `if (COMPACT_STRINGS && coder == LATIN1)` 整个分支被编译掉。

**问 3｜"源码里的 value[index] & 0xff 是什么意思？char 是一个字节？codePointCount 是字符个数？char 和 byte[] 都是二进制怎么区分？纯英文 StringLatin1 是不是就够了？牵扯中文或者表情就不行来？"**

解答：**char 不是 1 字节，是 2 字节**（16 位无符号，0~65535）；byte 是 8 位有符号（-128~127）。"Latin-1 模式下 1 字节存 1 个字符"说的是**存储宽度**，不是 char 类型的宽度——charAt() 返回时会把 1 字节扩成 2 字节的 char。

`StringLatin1.charAt` 源码一行：`return (char)(value[index] & 0xff);`。& 0xff 的作用是**改读法**：é 的字节 `11101001` 按 byte 有符号读是 -23（最高位当符号位），提升为 int 时高位补 1；拿 0xff（低 8 位全 1）一与，补出来的 24 个 1 全被清掉，只剩原始 8 比特 → 233 = é。比特本身没变，变的是解释方式。

StringUTF16 的 charAt 则是把两个字节拼起来：`(char)(((value[i] & 0xff) << 8) | (value[i+1] & 0xff))`。

"都是二进制怎么区分"：内存里的比特没有身份，**含义由"谁、按什么规则读它"决定**。同一串 `11101001`：有符号 byte 读 = -23；无符号读 = 233；在 Latin-1 字符串里 = é；当 UTF-16 的半个单元 = 无意义。类型告诉编译器读几位、按不按符号读；一块 byte[] 按 1 字节还是 2 字节一切，靠 coder 字段标记——**这正是 String 必须带 coder 的原因：裸的 byte[] 自身是歧义的**。

Latin-1 的能力线是 **U+00FF，不是"英文"**：é ü ñ（café）也够格；中文 U+4E2D、emoji、俄文、甚至拼音的 ā（U+0101）都不行。而且整串一票否决：`"caf中"` 里前三个字符也跟着翻倍。

codePointCount 数的是**码点个数**（每个真实 Unicode 字符算 1）——基本对，但注意它仍不等于"用户看到的字"：组合字符/复杂 emoji 是多个码点显示成一个字素。

**问 4｜"用一串二进制数具体说明下。"**

解答（四个字符的比特形态）：

| 字符 | 码点 | Latin-1 存储 | UTF-16 单元 |
|---|---|---|---|
| A | U+0041 | `01000001` | `00000000 01000001` |
| é | U+00E9 | `11101001` | `00000000 11101001` |
| 中 | U+4E2D | 装不下 | `01001110 00101101` |
| 😀 | U+1F600 | 装不下 | `11011000 00111101` + `11011110 00000000` |

场景一 `"Aé"`（Latin-1，coder=0）：内存 `[01000001][11101001]`。charAt(1) 的完整过程：

```
① value[1] = 11101001          ← 8 比特
② byte 有符号读：-23           ← 最高位被当符号位
③ 提升 32 位 int，负数补 1：    11111111 11111111 11111111 11101001
④ & 0xff：                      00000000 00000000 00000000 11111111
   =                            00000000 00000000 00000000 11101001 = 233
⑤ (char) 装进 16 位：           00000000 11101001 = U+00E9 ✓
```

场景二 `"A中"`（被迫 UTF-16，coder=1）：中 = U+4E2D > 0xFF，整串切双字节。charAt 取"中"：`((0x4E & 0xff) << 8) | (0x2D & 0xff) = 0x4E2D` ✓。length() = 4 >> 1 = 2。

场景三 `"A😀"`：😀 = U+1F600 > 0xFFFF，一个 16 位单元装不下，拆成**代理对**：高代理 0xD83D、低代理 0xDE00（高代理固定以 `110110` 开头、低代理以 `110111` 开头——扫描器靠这 6 个前缀比特认对）。length() = 6>>1 = **3**；codePointCount 把两个单元合成一个码点 = **2**。合成数学：`(0xD83D−0xD800)<<10 | (0xDE00−0xDC00)` + 0x10000 = 0x1F600 ✓。

同一串比特三种读法 = 乱码的本质：`01001110 00101101` 按 UTF-16 读是"中"；按 Latin-1 读变成 `N` 和 `-` 两个字符；按 GBK 查表得到完全无关的字。**乱码不是字节坏了，是解释规则对错了。**

**问 5｜"char 和 byte 的区别？"**

| | byte | char |
|---|---|---|
| 宽度 | 8 位 | **16 位（2 字节）** |
| 符号 | 有符号 -128~127 | 无符号 0~65535（Java 唯一无符号类型） |
| 语义 | 原始 8 比特，无固有含义（数据） | 天生是"一个 UTF-16 代码单元"（文本） |
| 用途 | 二进制 IO、网络、Compact Strings 的物理存储 | 文本处理，charAt()/length() 的计量单位 |

落到 IO：InputStream/OutputStream 是 byte 流（图片、压缩包），Reader/Writer 是 char 流（文本，内建编码翻译）。一句话：**byte 是无语义的 8 位有符号容器，char 是有语义的 16 位无符号字符单元**；byte 管占地，char 管含义，coder 负责把两边对上。

**问 6｜"意思就是 byte[] 每一个数据只能取值 0 到 7？char 呢，取值呢？"**

不是——8 个 bit 不是 8 个取值 0~7 的格子，而是 **8 个开关拼成的一个二进制数**。每个 bit 只能 0 或 1，8 个 bit 共 2⁸ = 256 种图案。é 的字节按权重算：128+64+32+0+8+0+0+1 = 233。

- byte 无符号读：0~255；有符号读（Java 默认）：-128~127，规则是最高位为 1 时值 = 无符号值 − 256（233 − 256 = −23）
- char：16 bit，2¹⁶ = 65536 种组合 → 0~65535（U+0000~U+FFFF），无负数

整数家族同一规律（位数 → 组合数 → 范围）：byte 8/256/−128~127；char 16/65536/0~65535；short 16/65536/−32768~32767；int 32/约 43 亿/−2³¹~2³¹−1。

**问 7｜"所以压缩只有在英文时是一致的？char 是 1 个字节是吧，字符呢，感觉这些概念没太理解。"**

先钉死四个词：**bit** = 开关（0/1）；**byte** = 8 bit，计量存储的单位；**char** = Java 的字符槽位，**恒定 2 字节，从不例外**，是 API 的计量单位；**字符** = 编号（码点），**没有大小**——"占几字节"永远要先问"用什么方式存"。同一个"中"：GBK 2 字节、UTF-8 3 字节、UTF-16 模式 2 字节。

修正两个说法：

1. **"char 是 1 个字节"——不是，char 永远是 2 字节。** 陷阱在于"Latin-1 模式 1 字节存 1 个字符"说的是存储层的占地，不是 char 类型变小了；charAt() 返回时会把 1 字节扩成 2 字节的 char。存储 1 字节 ≠ 类型 1 字节。
2. **"压缩只有在英文时"——边界更宽：看整串最大码点是否 ≤ U+00FF。** 纯英文必然满足；é ü ñ（café）也满足；混进一个中文/emoji/俄文 → 整串放弃压缩，所有字符一律 2 字节；emoji 更特殊——超 U+FFFF，还要占两个 char 槽位（代理对）。记法：**压缩是整串一票否决制，否决线是 U+00FF**。

自测三题：`"A"` 在 Latin-1 模式内存占几字节？——1 字节。`"A".length()` 的计量单位多宽？——char，2 字节，返回 1。`"A中"` 里那个 A 占几字节？——2 字节（被"中"拖进了 UTF-16 模式）。

**问 8｜"& 0xff 就是改读法……与运算是啥来的，我都忘了？"**

与（AND）：两串等长比特上下对齐，**逐列独立运算，双 1 才 1**。直观理解：`& 0` = 强制清零，`& 1` = 保持原样——所以 & 的用途是**掩码（mask）**：要保留哪几位就把掩码那几位设 1。亲戚四个：或 `|`（有 1 就 1，强制置位）、异或 `^`（不同才 1，翻转/交换）、非 `~`（取反）。

0xff = 十六进制 ff = `11111111` = 255（一个十六进制位对应 4 个 bit，字节正好写成两个十六进制位，如 0xE9 = 11101001）。

重走 & 0xff：

```
    11111111 11111111 11111111 11101001    ← (-23) 提升后的 32 位
  & 00000000 00000000 00000000 11111111    ← 0xff
  ─────────────────────────────────────
    00000000 00000000 00000000 11101001    = 233 ✓
```

高 24 位：掩码全 0 → 补出来的 1 全清；低 8 位：掩码全 1 → 原样放行。**& 是逐列"双 1 才过闸"，& 0xff 是只放行低 8 位的闸门。**

**问 9｜"-23 和 233 是怎么算出来的？"**

同一串 8 比特 `11101001` 的两种读法。无符号账本：按位置权重 128+64+32+0+8+0+0+1 = **233**。有符号账本（补码）：最高位权重变负（2⁷ 位当 **-128** 用），-128 + 64 + 32 + 8 + 1 = **-23**。

验算：取反加一 → `11101001` 取反 `00010110`(22) +1 = 23，所以原数是 -23。快速算法：最高位是 1 时，值 = 无符号值 − 256。

本质是 256 个比特图案排成一个**钟面**，无符号和有符号是同一批格子的两套标签：上半圈（最高位 0）标签一致（0~127），下半圈无符号叫 128~255、有符号整体减 256 叫 -128~-1。图案 233 站在 -23 的位置——**同一位置，两套名字**。这也是为什么补码下加法不需要特殊处理：-23 + 5 = 11101001 + 101 = 11101110（第 9 位溢出扔掉）= 238 − 256 = -18 ✓。

**问 10｜"最高位权重是 -128……如果要表示正的呢？0？105？"**

"-128 的权重"只在最高位**真的是 1** 时生效。统一公式：`值 = (-128)×b₇ + 64×b₆ + ... + 1×b₀`。b₇=0 时那一项贡献 0，正数照常表示：

```
01101001 → 0 + 64 + 32 + 8 + 1 = +105 ✓（正数没问题）
11101001 → -128 + 105 = -23                ← 同样的低 7 位，岔到负数区
```

低 7 位管"在半圈里的位置"，最高位管"站在上半圈还是下半圈"。0 = `00000000`（补码里零唯一，无 ±0 之分）。正数范围 0~127（128 个图案），负数 -128~-1（128 个）——所以 +128 在 byte 里表示不了，这就是范围写作 **-128 ~ 127** 的原因。

**问 11｜"好奇怪，我记得 408 组成原理里最高位只是符号位，只管正负，不考虑 -128 这种写法。"**

你没记错——那是**原码**的定义。408 讲了四种编码，同一串 `11101001` 有四个读数：

| 编码 | 规则 | `11101001` 读作 | 8 位范围 |
|---|---|---|---|
| 原码 | 最高位=纯符号标签，不参与数值 | **-105** | -127~+127（有 ±0） |
| 反码 | 负数 = 原码尾数按位取反 | **-22** | -127~+127（仍有 ±0） |
| 补码 | 反码+1；最高位权重 -2⁷ | **-23** | **-128~+127**（零唯一） |
| 无符号 | 全部按权重 | 233 | 0~255 |

正数在原码/反码/补码下完全相同（分歧全在最高位为 1 的负数区）。补码的定义式 `[x]补 = 2ⁿ + x (mod 2ⁿ)`：233 和 -23 正好差 256——同一图案的两套标签。硬件选补码弃原码的三个理由：零唯一（原码有 ±0）、加减统一成一个加法器、8 位用满 256 个图案（多出 -128）。移码（补码符号位翻转）用于浮点阶码——原反补移四兄弟各司其职。

**问 12｜"我明白了……你的方式是最高位负的高权重，后续正常相加？之前是取反加一换算。"**

完全正确，两种读法等价：

```
直读法：  11101001 → -128 + 64 + 32 + 8 + 1 = -23          （一步加权求和）
转换法：  11101001 → 取反 00010110(22) → +1 → 23 → 负号 → -23 （先求绝对值）
```

数学上同一回事：最高位为 1 的图案 u，直读 = u − 256；转换法 = 255 − u + 1 取负 = u − 256。补码本质是一个"最高位权重为负的进位制"，数字天生就是那个数，不需要转换。术语修正两点：取反+1 得到的是**绝对值**（不是"换成原码"）；低 7 位是**普通无符号二进制**（不是"原码计算"）。边界验证：`10000000` 直读 -128；取反+1 得 128 → -128 ✓，而这个 128 没有正数形态可回——负数比正数多一个名额的由来。

**问 13｜"intern 一般咋用？好像真实业务场景下不会使用到？"**

你的感觉对：业务代码几乎不手动调 intern。但 intern 机制每天自动运行两次：① **字符串字面量自动入池**；② **G1 String Deduplication**（JEP 192，JDK 8u20 引入 G1、JDK 18 起扩展，`-XX:+UseStringDeduplication`）——后台线程自动把内容重复的 String 底层数组指向同一份，不改代码。

手动 intern 的真实小众场景：解析器/词法分析器关键字表（匹配降为引用比较）、海量重复值瘦身。不用的原因：收益小（语义重复的值应该用 enum）、StringTable 是 native 固定大小哈希表（默认 65536 桶）、单 JVM 一份跨实例无意义。

**问 14｜"所以 intern 的作用是返回当前的 StringTable 里的重复的引用？"**

差半步——精确语义是两分支：

```
s.intern():
  按 s 的内容查 StringTable
   ├─ 池里没有 → 把 s 自己的引用装进池 → 返回 s 本身
   └─ 池里已有 → 什么都不加 → 返回池里那个旧引用（s 等着被 GC）
```

作用一句话：**把"内容相等"（equals）升级为"引用相同"（==）**——返回的是**规范引用**（canonical reference），不是"重复的引用"。池里存的是引用不是副本（呼应④段三个池）。省内存的前提是你**改用返回的那个引用**，旧副本不放手就白搭。

**问 15｜"如果要修改 z，是不是 a 也会被改了？？？"**

不会，两层原因。① String 没有"修改内容"这条路（内部数组私有、无写方法），"修改"只能让 z 改指向：`z = z + "!"` 新建对象，a 毫发无损。② 变量是各自的，对象是共享的——`z = ...` 只改 z 这个变量槽里的地址。对比可变对象：`sb2 = sb1; sb2.append("!")` 会让 sb1 真的被改——**共享引用不可怕，共享可变对象才可怕**。把场景推到 StringTable：规范对象全 JVM 共享，假如 String 可变，任何持有者改内容就是全局灾难——这正是"String 为什么设计成不可变"的场景化证明。

**问 16｜"其实本质就是节省空间，和前面的字符串压缩也是一个目的？"**

对了一半：都是**消除冗余**，但维度不同——Compact Strings 消除的是**单个字符串内部**的编码宽度冗余（改物理存储，API 语义零变化）；intern 消除的是**对象之间**的重复（改引用指向）。且 intern 的第一身份不是省内存，是**引用规范化**（让 equals 升级为 ==），省内存是有条件的副产品（要放手旧引用；字符串个个独一无二时反而白占表）。

**问 17｜"开启 -XX:+UseStringDeduplication 是不是就可以了？"**

取决于你想要什么——Dedup **根本不动引用**：

```java
String a = new String("something_long_repeat");
String b = new String("something_long_repeat");
// dedup 后：a == b 依然是 false！两个对象还是两个对象
// 但内部：a.value == b.value → 底层 byte[] 只剩一份
```

| 你想要什么 | intern | `-XX:+UseStringDeduplication` |
|---|---|---|
| 相等字符串引用相同（== 成立） | ✅ 但必须换用返回的规范引用 | ❌ 引用永远不变 |
| 相等字符串不占双份内存 | ⚠️ 有条件（要放手旧引用） | ✅ 全自动 |

Dedup 敢偷改 value 字段的前提恰是不可变——内容永不变化，共享底层数组无任何可观察差别。业务实践：判断字符串相等老实写 equals()，别追求 == 自动成立。

**问 18｜"手动 intern 管的是整个 String？dedup 只是底层的 byte[] 数组？"**

对，两个机制**下手的层级**不同：

| | 合并掉什么 | 保留什么 | 用户可见变化 |
|---|---|---|---|
| **intern**（对象级） | 重复的 String 对象（连人带数组） | 一个规范对象 | == 成立；要求换引用 |
| **dedup**（数组级） | 重复的内容数组 | 全部 String 对象 | 完全不可见 |

连带一个实际差别：dedup 只省数组那份钱，String 对象头（约 16 字节 + hash 等字段）一个没省——短重复串 dedup 省得有限，长串才痛快。intern 连对象头一起省，但要换引用配合。

### 与其他题的连线

## 02 · Builder、Integer、BigDecimal 的坑（Q15）【P1】

### 手册原文（解释版）

**① Builder 的长度和容量不是一回事。** StringBuilder 用可变存储和有效长度累积内容，容量足够时 append 复用空间，不足才扩容复制。JDK 8 常见候选容量是旧容量乘二加二。它没有保证多线程共同 append 的安全性；StringBuffer 的单方法同步也不能自动保护"检查再追加"的复合动作。

**② 包装整数必须区分引用与数值。** Integer 的 == 在两个包装引用间比较对象身份，缓存会让部分小整数碰巧共享对象。应使用 equals 或拆箱后比较，但拆箱 null 会抛 NullPointerException。

**③ 金额需要明确输入、精度与舍入。** new BigDecimal(0.1) 接收的是已经近似的二进制浮点数；用字符串或 valueOf 更符合十进制意图。1.0 与 1.00 的 equals 为 false（scale 不同），compareTo 为 0（数值相同）。除法要明确精度和舍入策略，实际舍入规则应来自业务。

### 会话问答

**问 1｜"它没有保证多线程共同 append 的安全性；StringBuffer 的单方法同步也不能自动保护'检查再追加'的复合动作——这句话不理解。"**

两个断言，分别打在 StringBuilder 和 StringBuffer 脸上：

**前半句：StringBuilder 连"单方法"都不原子。** 一次 append 内部至少三步（ensureCapacity 可能扩容 → 拷贝进数组 count 位置 → count += len），并发交错会丢更新（都读到 count=5 都往位置 5 写）、扩容竞态（A 换新数组 B 往旧数组写）、计数错乱。

**后半句：StringBuffer 每个方法都 synchronized——单次调用原子，但锁不住"两个方法之间"。**

```java
if (sb.length() < 10) {      // 调用 1：原子
    sb.append("xxxxxx");     // 调用 2：原子，但与调用 1 之间锁已释放
}
```

线程 A `length()=5 ✓` → 线程 B `length()=5 ✓` → 两个都追加 → 长度 15，"不足 10 才追加"的意图被击穿。**业务规则活在"两次调用"的跨度上，那里没有任何保护。** 修复：`synchronized(sb) { if (...) sb.append(...); }` 把锁的边界扩到和业务规则一样大。

**问 2｜"StringBuilder 不是多线程安全的，StringBuffer 是；JDK 里的方法应该都不是复合动作安全的吧，得自己来？"**

八九不离十，加两层精确化：

**JDK 方法分两档**：StringBuilder/HashMap/ArrayList 连单方法都不原子；StringBuffer/Vector/Hashtable/CHM 单键操作单方法原子。**两档对复合动作一律不保**，且复合动作比想象的隐蔽——检查再行动、先读后写、**迭代**（`Collections.synchronizedList` 的 javadoc 明文要求迭代时手动同步）。

**为什么 JDK 不能保**：库知道数据结构，不知道你的业务不变量——"不足 10 才追加"只存在于调用方代码里。

**三条出路**：① 把复合塞进单次调用（putIfAbsent/compute）；② 自己圈范围（synchronized/ReentrantLock）；③ **状态坍缩**——N 个相关字段打包成一个不可变对象，全并发只碰一个 volatile/AtomicReference 引用，"改 10 个字段"坍缩成"换 1 个引用"。CopyOnWriteArrayList 是这个思想的容器版。

统一理论：**容器的"线程安全"承诺只到单次操作；复合动作（检查再行动、先读后写、迭代）永远自己负责**——这句话同时覆盖 Q22 的 CHM 与事务。

### 与其他题的连线

Q22：本文的"单方法原子 vs 复合动作"与"单键原子 vs 跨键事务"是同一条边界线。Q14：StringBuilder 可变共享的事故，反向解释 String 为什么不可变。Q17：迭代是复合动作的教科书案例。

## 03 · subList、迭代器、fail-fast（Q17）【P1】

### 手册原文（解释版）

**① subList 是视图，通常不是复制。** 对父列表 [A,B,C,D] 调用 subList(1,3)，视图为 [B,C]。视图 set(0,X) 会把父列表变成 [A,X,C,D]。父列表在视图外发生结构修改后，继续使用原视图可能失效或抛 ConcurrentModificationException。视图可能保留父列表及其大数组，长期留存小切片应考虑 new ArrayList<>(view)，但元素对象仍是同一批引用。

**② fail-fast 是查错机制，不是并发协议。** 迭代器记录创建时的修改计数，遍历中比较 modCount 与期望值来尽早暴露非法结构修改。这是尽力检测，不能承诺所有并发错误都被捕获。教学例：增强 for 中直接 list.remove，后续迭代可能抛异常；使用 iterator.remove 则会正确更新该迭代器的期望计数。批量删除也可用 removeIf。

**③ 固定长度和不可修改不同。** Arrays.asList 由原数组支持，允许 set，通常不允许 add/remove。JDK 9 起的 List.of 不允许修改，也不接收 null。Collections.unmodifiableList 是包装视图，底层列表仍可能被别处修改；不可修改容器也不冻结元素对象。

### 会话问答

**问 1｜（题目讲解）三点的最小实验。**

```java
// ① subList 是视图
List<String> sub = list.subList(1, 3);
sub.set(0, "X");
System.out.println(list);        // [A, X, C, D] ← 父列表被改了
list.remove(0);                  // 视图外动父结构
sub.get(0);                      // → ConcurrentModificationException —— 视图作废

// ② 遍历中直接删 → CME；正确姿势 iterator.remove() 或 removeIf

// ③ 三种"不能改"：Arrays.asList 定长（set 可、add/remove 不可、底层同一数组）
//    List.of 冻死（全不可、拒 null）；unmodifiableList 只读包装（自己不能改，底层改了跟着变）
```

一句话区分：**asList = 定长、List.of = 冻死、unmodifiable = 我不改 ≠ 别人不改**；三者都不冻结元素对象。

**问 2｜"modCount 会不会触发上限？"**

modCount 是普通 int（AbstractList.java:630），Java int 溢出是**无声回绕**——数到 21.47 亿变负继续，不抛异常不清零，所以不存在"上限触发"。回绕无害的原因：检查是裸的 `!=`（ArrayList.java:1095），回绕后照样对不上、照样抛 CME。唯一的漏检窗口：迭代器活着期间列表恰好被修改 2³²（42.9 亿次）的整数倍——每秒百万次也要 70 多分钟不间断、且迭代器一次 next() 都不调，实践不可达。真正要注意的：modCount **非 volatile**（fail-fast 不是并发协议的物理基础），以及它一鱼多吃。

**问 3｜"它一鱼多吃……这个不理解。"**

modCount 本质是"结构变动流水号"。所有需要"记住位置"的东西按同一协议工作：**创建时抄一份流水号 → 使用前对账 → 对不上抛 CME**。这个协议被复制到三处：

1. **ArrayList 自己的迭代器**：抄 modCount，next() 前查 `modCount != expectedModCount`。
2. **SubList**：它没有自己的存储，只是"父列表 + offset"的透镜——get(0) 实际执行 `root.elementData[offset+0]`。父列表一动 offset 全错，所以它对账的对象是**根列表的账**（root.modCount）。"视图外改父列表 → 视图作废"不是保护用户，是它自救：不对账它自己就会取错元素。
3. **HashMap/HashSet**：不继承 AbstractList 拿不到字段，另立一本同款 modCount，HashIterator 同款协议。

**问 4｜"源码展示一下呢。"**

JDK 25 ArrayList.java 实测（行号可查）：

```java
// 构造时抄账（:1205）
public SubList(ArrayList<E> root, int fromIndex, int toIndex) {
    ...
    this.modCount = root.modCount;        // ★ 把根账本抄一份
}

// 增删三步曲：对账 → 传导 → 记账（:1242）
public void add(int index, E element) {
    rangeCheckForAdd(index);
    checkForComodification();             // ① 用前对账
    root.add(offset + index, element);    // ② 传导给根列表（真账 +1）
    updateSizeAndModCount(1);             // ③ 自己人记账
}

// 记账方法：连父视图的账一起记（:1501）
private void updateSizeAndModCount(int sizeChange) {
    SubList<E> slist = this;
    do {
        slist.size += sizeChange;
        slist.modCount = root.modCount;   // ★ 抄本 = 根账本最新值
        slist = slist.parent;             // ★ 沿 parent 链，每层祖先视图都同步
    } while (slist != null);
}

// SubList 自己的对账（:1497）
private void checkForComodification() {
    if (root.modCount != modCount)        // 根账本 vs 我抄的
        throw new ConcurrentModificationException();
}
```

parent 链服务"视图的视图"：内层视图加元素，外层的 size 和偏移也变了，每层祖先的抄本都要同步。**反向对照**：SubList.set（:1222）直接写数组、**没有** updateSizeAndModCount——set 不改长度、真账没动，抄本自然还是对的。这就是手册追问"set 为什么不触发异常"的源码级答案。

统一规律：**所有结构性写操作，最后一步把抄本对齐真账；所有依赖位置的操作，第一步检查抄本是否等于真账。** 自己人写 → 写完顺手对齐 → 下次对账通过；外人写 → 对账失败 → CME。

**问 5｜（延伸）Collections.synchronizedXxx、RandomAccess、泛型擦除 → 见第 07 章延伸专题。**

## 04 · HashMap put/get、扩容（Q18）【P0】

### 手册原文（解释版）

**① 先按散列缩小范围，再比较键。** 键的 hashCode 经高低位扰动后，以 (n-1)&hash 定位；容量取二的幂，让掩码运算可覆盖全部桶。get 找到桶后还要核对散列以及 equals。put 匹配已有键就更新值，不匹配才插入；因此碰撞不等于覆盖。容量16掩码15是1111可覆盖0–15；容量10掩码9是1001只会产生0、1、8、9等下标。

**② 容量、数量、阈值各有作用。** capacity 是桶数组长度，size 是映射数量，扩容阈值通常是容量乘负载因子。默认构造不马上分配数组，第一次 put 才初始化。预设容量要考虑负载因子。

**③ 扩容为什么只需检查一位。** 容量从 16 变 32，旧下标为 hash&15，新下标为 hash&31。hash 的 16 这一位为 0 节点仍在原下标；为 1 则去原下标加 16。节点已保存散列，无需再次调用 hashCode。JDK 7 头插转移的历史环链问题不能当作 JDK 8 同一路径的解释，但 8 仍存在数据丢失与错误观察风险。

### 会话问答

**问 1｜"hash = h ^ (h >>> 16); index = (n-1) & hash; 解释下。"**

先讲第二步（它是第一步存在的理由）：`(n-1) & hash` 中 n 恒为 2 的幂，n-1 是**全 1 掩码**（16→1111），与运算等价于 `hash % n` 但只需一条指令。它只保留 hash 的低 log₂n 位——**高 28 位全被无视**。如果两个 hashCode 只在高位不同、低位相同，直接同桶。

第一步就是修这个问题：`h ^ (h >>> 16)` 把高 16 位折叠进低 16 位——**让低位携带着高位的信息**。`>>>` 是无符号右移（`>>` 负数补 1 会污染数据）；用 `^` 而不用 `&`/`|` 是因为异或不偏不倚、可逆、不丢信息。反例验证：`h₁=0x00010001, h₂=0x00020001` 低位全同，折叠后低 4 位 0000 vs 0011，分开了。为什么恰好 16：hashCode 32 位，桶数组极少超过 2¹⁶，取一半移一半最平衡。

**问 2｜"把高位'搬进'低位是啥意思，没懂？"**

比喻不严谨——XOR 根本不移动比特。准确说法：**让低位的计算结果受高位影响**。8 位缩小实验（掩码取低 4 位）：

```
k1: 1010 0001    k2: 0110 0001     高4位不同、低4位相同
h>>>4 之后，原高4位正好落在低4位的位置上
新低位的每一位 = 原低位对应位 ⊕ 原高位对应位

k1: 1010 0001 ^ 0000 1010 = 1010 1011 → 低4位 1011
k2: 0110 0001 ^ 0000 0110 = 0110 0111 → 低4位 0111
扰动前都是 0001（同桶），扰动后分开 ✓
```

高位没有动，是低位的"身份"变了——从"只由自己决定"变成"由全宽 hash 共同决定"。这个手法叫**对折异或（xor-fold）**：32 位对折成两半逐位异或，折叠后的低位每一位都是原来两个位置的函数——掩码读到的不再是截断的尾巴，而是**整个 hashCode 的折叠摘要**。

**问 3｜"为啥要这样做？不是直接 hash？"**

直接 `(n-1) & h` 功能上是对的——问题是**低位不一定可靠**。hashCode 是人写的，带规律：`Integer.hashCode()` 就是值本身；数据库主键、时间戳常是连续或成倍数的。例：键 65536、131072、196608（0x00010000/0x00020000/0x00030000）——低 16 位全是 0，直接掩码全进 0 号桶，哈希表退化成链表。加扰动：0x00010001、0x00020002、0x00030003 → &15 得 1、2、3，分开。

所以扰动不是优化，是**防御层**：哈希表 O(1) 的承诺依赖低位均匀分布，而 JDK 无法假设使用者写出的 hashCode 低位不扎堆。两个边界：扰动救不了低位就相同的键（0、16、32——树化兜底）；JDK 8 刻意只做一次 XOR（JDK 7 是多轮混合），因为树化已把最坏碰撞压到 O(log n)，定位环节求快不求完美。

**问 4｜"index = (n-1) & h 的决定权只有低位，是因为 n-1 吗？为啥是 n-1 而不是 n？"**

是的，而且用 n 根本没法当下标。AND 的规律：**掩码里每个 1 是一条放行通道，每个 0 是一堵墙——决定权 = 掩码里 1 的个数**。

```
n    = 16 = 0001 0000    只有一个 1 → 结果只有 0 或 16 两种，且 16 越界
n-1  = 15 = 0000 1111    四个 1 → 结果 0~15，正好铺满全部下标
```

为什么 n-1 恰好全 1：2 的幂 = 1 后面一串 0，减 1 借位后 0 全翻 1（10000−1=01111）。一般化：2^k − 1 = k 个连续的 1——决定权的 bit 数正好够表达 n 种下标。附带：n 是 2 的幂时 `h & (n-1)` 恒等于 `h % n`；n=10 时 n-1=1001 不全 1 → 只有 0、1、8、9 可达——这就是"容量必须 2 的幂"的原因。

**问 5｜"扩容是怎么扩容的？"**

四个阶段（JDK 25 HashMap.java:684 实测）：

```
① 触发：putVal 末尾 if (++size > threshold) resize()  —— 先插后查
② 建表：newCap = oldCap << 1，newThr 翻倍，分配新数组
③ 搬运：遍历旧表逐桶，三种情况——
   单节点：newTab[e.hash & (newCap-1)] = e 直接放
   树桶：TreeNode.split 拆两侧，某侧 ≤6 退化回链表
   链桶：按 (e.hash & oldCap) 拆成 lo/hi 两条尾插链
         == 0 → lo 链 → 新表[j]（原地）
         != 0 → hi 链 → 新表[j + oldCap]（搬去 +16）
④ 收尾：oldTab[j] = null 帮 GC；无锁、O(n)、保序
```

判据 `(e.hash & oldCap)` 的设计：oldCap = 16 = `0001 0000`，本身就是"新开放那一位"的**单位掩码**——一次 AND 直接读出新掩码多开的那一位是 0 还是 1。容量 4→8 的走查：桶3=[3,7,11]，`3&4=0` 留 3、`7&4=4` 去 7、`11&4=0` 留 3 → 新表桶3=[3,11]（保序）、桶7=[7]。验证：3&7=3 ✓ 7&7=7 ✓。

**问 6｜"扩容都是翻倍吗？"**

主路径都是（`oldCap << 1`，被掩码技巧和均摊 O(1) 双重锁死——×1.5 会破坏 2 的幂，就得退回逐节点重算）。三个例外：

- **首次建表不是翻倍**（懒初始化）：`new HashMap<>(1000)` 首次 put 建表 1024（tableSizeFor），但阈值是 1024×0.75 = 768——填到 769 条照样翻倍到 2048。想全程不扩容传 `1000/0.75 ≈ 1334`。
- **封顶**：容量到 1<<30（约 10.7 亿）不再扩，阈值拉满，碰撞靠红黑树硬扛。
- **从不缩小**：remove 一百万条、clear() 都不缩容——HashMap 没有 trimToSize。

## 05 · ConcurrentHashMap 读写、扩容（Q21）【P0】

### 手册原文（解释版）

**① JDK 8 把写竞争限制在桶附近。** 空桶安装首节点通常通过 CAS；非空桶写入通常同步桶头并重新确认，再在链或树内更新。不同桶可并行处理；JDK 7 的 Segment 分段锁模型不能直接用来解释 8。

**② 读为何通常不拿写入的桶锁。** 表槽访问以及节点的关键字段提供所需可见性。仅说 table 是 volatile 不够：volatile 数组引用保证的是引用的读写，不会自动让每个数组槽变成 volatile。

**③ 扩容可以让多个线程协作。** 旧桶已搬到新表，旧槽放 ForwardingNode，读者遇到它转向新表，写线程也可能加入搬迁。sizeCtl 在初始化、正常阈值和扩容阶段承担不同控制含义。并发时 size 只能作为观察统计。

### 会话问答

**问 1｜"ForwardingNode 是什么？"**

扩容期间放在旧桶里的**哨兵节点**：`static final int MOVED = -1`，没有 key/value，只持有 nextTable（新表）的引用。作用：旧桶搬完后旧槽不能放 null（并发读会误判"键不存在"），放一个"墓碑 + 转发指针"。撞上它时——**读**：顺着 nextTable 到新表找（ForwardingNode.find()），无锁不阻塞；**写**：这个桶写不进了，线程检查 sizeCtl 发现扩容进行中，就加入搬桶大军（经 transferIndex 认领桶区间），搬完在新表重试——"把等待变成帮忙"。sizeCtl 是状态机：正数=阈值、-1=初始化中、其他负数（带扩容戳）=扩容中+参与线程数。

**问 2｜"compute 是啥来的，没印象了？"**

JDK 8 给 Map 加的**原子读-改-写**方法之一。没有它时计数要 `get → 判空 → put` 两步，并发下丢更新；`map.compute(key, (k, v) -> v == null ? 1 : v + 1)` 或 `map.merge(key, 1, Integer::sum)` 把三步捏成一次调用。在 CHM 上，这次调用内部对桶加锁——是 CHM 提供的最强单键原语，Q22 说的"单次原子边界"就是它。

**问 3｜"这几个方法没看懂，执行流程是怎样的？"**

五个方法 = 同一个"查旧值 → 判断 → 调回调 → 写结果"骨架的五种变体：

| 方法 | 键不存在时 | 键存在时 | 回调返回 null 的含义 |
|---|---|---|---|
| compute | 调回调（oldValue=null），非 null 插入 | 调回调，非 null 覆盖 | **删除该键** |
| computeIfAbsent | 调回调，非 null 插入 | **不调回调**，返回旧值 | 不插入 |
| computeIfPresent | 不调回调 | 调回调，非 null 覆盖 | **删除该键** |
| merge | 不调回调，直接放 value | 调回调(旧值， 新值) | **删除该键** |
| putIfAbsent | 直接放 value | 不放，返回旧值 | （无回调） |

易踩差异：compute 系回调参数 (key, 旧值)，merge 是 (旧值， 新值)；putIfAbsent 返回旧值，compute 系返回最终新值。**这些方法在 HashMap 上仍是两步、不原子**——原子性是 CHM 重写后塞进桶锁的结果。

CHM 里 compute 的执行流程：定位桶 → 空桶 CAS 放占位节点（ReservationNode，值要等回调跑完才知道）→ 桶头是 ForwardingNode 先帮忙扩容再重试 → 普通节点 synchronized(桶头) 锁内复查再跑回调写回 → addCount。回调的三个约束：**短**（持桶锁，查库会阻塞同桶线程）、**可重算**（返回 null/抛异常/被删都会导致回调再跑，副作用必须可重复）、**不递归**（回调里再 compute 同 Map 可能死锁，JDK 9+ 抛 Recursive update）。

## 06 · CHM 能替代业务事务吗（Q22）【P1】

### 手册原文（解释版）

**① 原子方法保护明确的单次边界。** putIfAbsent 可原子地"没有才放"，compute 可把同一键的读、计算、更新放到受控范围内。普通 get 后再 put 仍是两步。若值是可变对象，把它放在并发 Map 中不会自动保护对象内部字段。

**② 多键约束需要另外的机制。** 教学例：A 账户减 10、B 账户加 10，哪怕两次 compute 分别原子，中间仍可能被读取到只扣未加，第二步失败也没有自动回滚。要维护跨键不变量，可以用共同锁、不可变整体状态加原子替换，或在数据库事务中完成。

**③ 计算回调不是永久只执行一次的缓存承诺。** computeIfAbsent 返回 null 就不建立映射，抛异常也不留下成功结果，删除后再次请求还会重算。回调应短且不递归修改相关映射。CHM 禁止 null 键和值，让 get 的 null 可以清晰表达当前没有映射。

### 会话问答

**问 1｜"CHM 和事务怎么会联系到一起？"**

这道题抓住的是一个真实设计失误。业务里很多操作就是"改内存里的一个 Map"（幂等去重、计数、缓存、状态流转），于是有开发者会想："CHM 的 compute 是原子的，那我这套业务逻辑是不是连数据库事务都不用开了？"

面试官问"CHM 能替代业务事务吗"，就是在问这个想法对不对。两者不在一个维度：**CHM 解决并发安全**（多线程改共享数据不坏、单次操作不丢），**事务解决一致性**（一组业务动作面对崩溃和并发保持业务一致、可回滚）。前者是后者的前提之一，远远不是后者本身。

用保险支付走一遍（三个动作：订单标已支付 → 扣钱 → 保单生效）：

- **故障**：第 2 步前进程崩 → 订单已"已支付"、钱没扣。CHM 没有回滚概念，甚至不知道这三个 put 属于同一笔业务。
- **并发可见**：另一线程在第 1、2 步之间读状态 → 看到中间态。CHM 对跨操作隔离没有任何承诺。

答题路径（结合保险金融背景）："不能。CHM 的原子性只到单键单操作；多步一致性必须落数据库事务（或 Outbox/TCC），配合事件 ID 唯一约束在同一个事务里去重并变更业务，提交后 ACK；外部接口另带幂等键；账务约束和对账兜底。内存 Map 只承载单键语义的场景——计数、去重、缓存。"

### 与其他题的连线

Q21：桶锁粒度是"单键原子"的物理来源。Q15：StringBuffer 的"检查再追加"与本文"跨键转账"同一条边界线；三条出路对应"共同锁/不可变状态+原子替换/数据库事务"。Q18：HashMap 第一档、CHM 第二档，复合动作两档都不保。

## 07 · 跳表与 ConcurrentSkipListMap（延伸）

> 背景：讨论"TreeMap 是并发的吗"引出的完整专题。先说结论：**TreeMap 不是线程安全的**，并发有序 Map 的 JDK 内置答案是 `ConcurrentSkipListMap`——它用跳表（skip list）而不是红黑树。

### 会话问答

**问 1｜"TreeMap 是并发的吗？"**

不是——和 HashMap、StringBuilder 同一档，所有方法无同步，并发写会让红黑树正在旋转时被读写、指针错乱。真正的问题是：**需要"并发 + 有序"时用什么？** 答案 ConcurrentSkipListMap，它不选红黑树是有原因的：

红黑树的插入删除依赖**旋转**，一次旋转改变一串节点的父子关系（子树整块搬家），锁的粒度只能覆盖整棵受影响子树——并发红黑树复杂到没有工程价值，JDK 一直没采用。跳表（多层链表，底层全量、上层索引递减，查找从顶层走、走不动下移，期望 O(log n)）的**平衡性靠随机**——每个新节点的层数抛硬币决定，不需要旋转和全局信息。

代价：概率平衡（最坏 O(n) 但概率可忽略）、每节点多层指针内存更高、常数因子大——**单线程 TreeMap 更快**。选型表：单线程有序 → TreeMap；并发有序 → ConcurrentSkipListMap（内置唯一选择）；并发无序 → CHM。

**问 2｜"插入/删除只改相邻几个节点的 next 指针，用 CAS 原子替换即可——没有旋转这种'牵一发动全身'的操作。这个不明白。"**

关键在 **CAS 一次只能改一个内存字**，所以问题变成：跳表插入需要改几个字？改到一半合法吗？

跳表插入 40（链 `... 30 → 50 ...`），改动一共两笔：

```
① 40.next = 50       （新节点自己的字段，无竞争）
② 30.next = 40       （一个 CAS：把 30 的 next 从 50 换成 40）
```

其他所有节点一个比特没动。**中间状态合法**：① 之后 40 存在但没人指向（不可见），链表还是原样；② 一执行 40 原子出现。

对比红黑树旋转的改动清单（LL 修复）：更上层结点改指 P、G.left 改指 β（子树整块搬家）、P.right 改指 G、P/G 变色——**四步必须打包生效，中间任何一步都是非法红黑树**。CAS 是"一次一个字的螺丝刀"，拧得动两笔的链表插入，拧不动四笔的事务。

更深一层：**一个操作需要读谁的状态，就得和谁同步**。跳表的平衡来自每个节点自己的随机层数（插入只看自己）；红黑树的平衡来自全树颜色约束（修复要读父、叔、祖）。

**问 3｜"如果一个线程插入、一个线程删除怎么说？怎么锁？CAS 代码看看，包括跳表的结构。"**

先纠正用词：同一进程里的多个**线程**（进程间不共享内存，CAS 无从谈起）。

**结构**（JDK 25 ConcurrentSkipListMap.java:360/374，实测）：

```java
static final class Node<K,V> {      // 基层·数据层：所有键值对
    final K key;
    V val;                          // null 表示"已逻辑删除"
    Node<K,V> next;
}
static final class Index<K,V> {     // 索引层：不存数据
    final Node<K,V> node;           // 指向基层节点
    final Index<K,V> down;          // 下一层
    Index<K,V> right;               // 同层右边（唯一会变的字段）
}
// HeadIndex 记录最高层；新节点以 1/4 概率建索引（(lr & 0x3) == 0）
```

注意 JDK 22+ 重写过：字段不再是 volatile，改用 VarHandle（NEXT/VAL/RIGHT）——老教材的 `casNext(n, f)` 对应这里的 `NEXT.compareAndSet(...)`。

**插入**（doPut:650）就一笔 CAS：

```java
if (c < 0 && NEXT.compareAndSet(b, n, p = new Node<K,V>(key, value, n))) { ... }
// 新节点构造时 next 已指向 n（预指向），CAS 只改前驱 b 的 next
```

**删除**（doRemove:758）分三步：

```java
else if (VAL.compareAndSet(n, v, null)) {   // ① 逻辑删除：val 置 null（打标）
    result = v;
    unlinkNode(b, n);                        // ② ③ 物理摘除
    break;
}

static <K,V> void unlinkNode(Node<K,V> b, Node<K,V> n) {   // :415
    for (;;) {
        if ((f = n.next) != null && f.key == null) {
            p = f.next; break;               // marker 已被别人插好
        }
        else if (NEXT.compareAndSet(n, f, new Node<K,V>(null, null, f))) {
            p = f; break;                    // ★ 插 marker 哨兵
        }
    }
    NEXT.compareAndSet(b, n, p);             // 前驱跳跃：跨过 n 和 marker
}
```

**一个线程插 40（30 后面）、一个线程删 30 的时序**（链 `20 → 30 → 50`）：两个线程的战场都在 **30.next** 这个字段上，CAS 天然互斥——谁先成功，另一个的期望值必然对不上：

```
时序 A（插入先成功）：30.next: 50→40 ✓ → T2 标记 30.val=null → 插 marker（30.next: 40→marker）
                     → 前驱跳跃 20.next: 30→40 → 链 20→40→50，40 完整落位 ✓
时序 B（删除先标记）：30.next: 50→marker ✓ → T1 的 CAS 期望 50、实际 marker → 失败 ✗
                     → T1 重走 findPredecessor → 在正确位置重试 ✓
```

**怎么锁？——不锁，整个类零锁。** 冲突处理三个动作：CAS 失败重试；**helping**（源码里到处是 `else if ((v = n.val) == null) unlinkNode(b, n)`——任何线程撞到已删节点顺手帮忙摘除，删除线程挂了垃圾照样被收）；弱一致读（doGet 撞到标记节点顺手清理索引）。这是 lock-free 的定义兑现：任何线程挂起，其他线程的整体进度不受影响。

**问 4｜"marker 没看懂。"**

根源：**插入和删除动的是两个不同的字段**。T1 插 40 改 `30.next`，T2 删 30 改 `20.next`——CAS 只能保证**同一个字段**上的互斥，两个字段互不设防，两个 CAS 都能成功：

```
T1: CAS(30.next, 50 → 40) ✓     30 后面挂上了 40
T2: CAS(20.next, 30 → 50) ✓     20 直接跳到 50
结果：20 → 50                   40 只被 30 指着，凭空消失
```

marker 的本质：**把删除的战场搬到和插入同一个字段上**。删除第一步先去改 30.next（插 marker 占位），从此所有"插到 30 后面"的 CAS 期望值必然对不上，只能失败重走——插入和删除开始抢同一个字段，CAS 的互斥性终于生效：一胜一败，绝不双赢，绝不丢数据。

marker 和 `val = null` 标记的分工（缺一不可）：`val = null` 贴在 30 自己身上，**管读**——遍历者认出尸体、跳过或帮忙摘除；marker 是 30 后面的路障，**管写**——堵死"往死人后面插入"的窗口。只有前者没有后者 → 丢插入；只有后者没有前者 → get(30) 还能返回值。

**问 5｜"本质问题难道不是 40 还没来得及和 50 关联吗？？？"**

抓的是"半个本质"。真实实现里，`NEXT.compareAndSet(b, n, p = new Node<>(key, value, n))`——新节点**构造时** next 就指向 n(=50)，40 挂上链的时候是完整链接的（30 → 40 → 50），不存在"未关联"窗口（实现故意把三步压缩成一次 CAS，先消灭了这类竞态）。

真正的本质：**删除用的是旧后继快照**。T2 在"读到 30 的后继是 50"和"CAS 20.next = 50"之间，30 的真后继已经变成 40——T2 的跳跃绕过了中间真实存在的节点。

marker 的作用重新表述：`CAS(30.next, 50 → marker)` 自带校验——**只有 30.next 仍然是 50 才能成功**。成功即宣布"30 和 50 之间永远不会再有新节点"，于是物理摘除时写的 50 不再是陈旧快照，而是被 marker **冻结**的当前真值。你的"未关联"判断对三步式插入的实现成立——那个隐患被"构造即链接 + 单次 CAS 发布"消灭，剩下的才轮到 marker。

**问 6｜"marker 是一个节点？怎么挂上的，怎么判断的？"**

是真实的 Node 对象：`new Node<>(null, null, f)`——key、val 全 null，next 出生时就指向 f。挂上 = 一次 CAS 换 30.next 的指向（marker 的 next 在构造时已接好，和普通插入同款"预指向"技巧）。判断靠 **key == null 指纹**：ConcurrentSkipListMap 禁止 null 键（doPut 第一行对 null key 抛 NPE），所以真实数据节点的 key 永远不为 null——key == null 被"征用"为 marker 的唯一身份标识。

判断规则一览：

| 节点特征 | 是什么 | 遍历者遇到时的动作 |
|---|---|---|
| key ≠ null，val ≠ null | 正常数据节点 | 比较、推进 |
| key ≠ null，val = null | 已逻辑删除的数据节点 | 顺手 unlinkNode 摘除 |
| key = null | marker 哨兵 | 跳过：取 marker.next 继续；插入者重走定位 |

marker 的生命周期：出生在 unlinkNode 的 CAS 里 → 挂链的唯一作用是堵住插入窗口 → 和被删节点一起被前驱跳跃跨过 → GC。它不参与排序（永远走不到比较那步）、不参与查找、不计入 size。

**问 7｜（确认）"其实就是插入了一个节点，key、val 都是 null，next 是之前读取的下一个节点。"**

对，一字不差。补一个小闭环：next 里存的 f 是**带校验的**——挂 marker 的 CAS 期望值就是 f，成功即保证 f 仍是 30 的真实后继，后续跳跃不会绕过任何活节点。删除的全部逻辑三行：`val = null`（贴标签，管读）→ 插 marker（占坑，管写）→ 前驱跳跃（收工）。

### 与其他题的连线

Q21：CHM 的桶锁 + 弱一致迭代与跳表的无锁 + 弱一致是并发容器的两种实现路线。Q19：跳表的概率平衡 vs 红黑树的确定性平衡——408 只考后者，跳表是纯工程知识。Q17：遍历中撞到已删节点顺手帮忙摘除，与 fail-fast 的"尽力而为"同族但方向相反（一个帮忙修复、一个报警退出）。

## 08 · 延伸专题：synchronizedXxx、RandomAccess、协变与擦除

> 从 Q17/Q18 讨论延伸出的三个专题，源码验证自本机 OpenJDK 25。

### 会话问答

**问 1｜"Collections.synchronizedXxx 是怎么保证同步的？源码没看出来。"**

同步逻辑不在工厂方法里，在 `Collections` 的**私有内部类**（Collections.java:2287 起）——标准的**装饰器模式**：

```java
static class SynchronizedCollection<E> implements Collection<E>, Serializable {
    final Collection<E> c;   // 被包的真实集合
    final Object mutex;      // 锁对象
    SynchronizedCollection(Collection<E> c) {
        this.c = c; mutex = this;     // ★ 默认拿包装器自己当锁
    }
    public int size() {
        synchronized (mutex) { return c.size(); }   // 每个方法：抢 mutex → 转发
    }
    public Iterator<E> iterator() {
        return c.iterator(); // Must be manually synched by user!
    }
}
```

三个关键：① `mutex = this`——迭代时要 `synchronized(返回的list)` 才抢得到同一把锁；② `iterator()` **故意不同步**（迭代器交出去后 wrapper 失控，每次 next() 上锁也没用——复合动作问题）；③ **绕道陷阱**——谁攥着原始引用谁就绕开全部同步。

**问 2｜"RandomAccess 有啥用？"**

空标记接口（接口体就一个 `{}`）——用"类型"本身携带一条性能承诺：`get(i)` 近似 O(1)。ArrayList/Vector/CopyOnWriteArrayList 有标记，LinkedList 没有。JDK 里十余个算法按它分支（binarySearch/shuffle/reverse/fill/copy/rotate）：`if (list instanceof RandomAccess || list.size() < THRESHOLD)` → 下标直达版 / 迭代器版，防的正是"对 LinkedList 做下标循环"的 O(n²) 事故；小列表不值得分支（量小免优化）。synchronizedList 的三元选择就是把标记延续下去——**写自己的 List 装饰器要把标记传下去**。同家族：Serializable、Cloneable（注解诞生前的类型级元数据）。

**问 3｜"本质原因是泛型？泛型擦除？"**

不是。擦除管"类型参数"（`List<String>` 与 `List<Integer>` 运行时同一个 Class）；RandomAccess 管"实现特征"（ArrayList 还是 LinkedList），与类型参数无关。反证：C# 泛型是真类型（无擦除），判断随机访问能力依然要运行时检查或接口拆分。本质链：**一个 List 接口统一了数组背和链表背 → 接口只能约定行为、不能约定复杂度 → 运行时唯一信息通道是具体类型 → 空标记 + instanceof**。可选替代设计是子接口 RandomAccessList extends List，标记接口胜在正交。

**问 4｜"泛型擦除好像会导致什么问题，很经典的。"**

证明擦除的最短代码：`new ArrayList<String>().getClass() == new ArrayList<Integer>().getClass()` → true。

编译期禁止五件事：`instanceof List<String>`；`new T()` / `new T[]` / 泛型数组（数组协变+运行时检查的组合在擦除后无法实现，会留堆污染隐患）；静态成员用类的 T；泛型类 extends Throwable / catch 泛型类型；`f(List<String>)` 与 `f(List<Integer>)` 重载撞车。

运行期两个经典易错点：反射破坏泛型后错误延迟到读取点（反射往 `List<Integer>` 里塞字符串，打印正常、get 时才 CCE——堆污染）；覆写泛型父类方法生成桥方法，反射/AOP 会看到两个签名。

**高级精确点**：擦除丢的是"实例的类型参数"——对象头 klass 指针永远精确指向真实类；声明处的泛型留在字节码 Signature 属性里（所以 Jackson 的 `new TypeReference<List<User>>(){}` 能经 getGenericSuperclass 读到——匿名子类是真实存在的类）。**擦除抹掉的是"某次实例化的实参"，它从未在运行时存在过。** 为什么这么设计：JDK 5 时代的迁移兼容——raw 集合代码不重编译就能混用。

**问 5｜"数组协变是什么意思？为什么 List<String> 不是 List<Object> 的子类型？"**

协变 = 子类型关系穿透容器：`String[] → Object[]` 被允许。事故路径：`objs[0] = 42` 编译通过、**运行时当场 ArrayStoreException**（数组对象自带组件类型，每次写入核对）——异常在写入点被拦截。若 List 也允许协变：`objs.add(42)` 编译通过，`strs.get(0)` 才 CCE——**异常在无辜的读取点抛出**（擦除后无检查可做）。所以泛型唯一安全的选择是不变——把错误拦在编译期。

普遍规律：**只读（生产者）→ 协变安全；只写（消费者）→ 逆变安全；可读可写 → 必须不变**。List 是读写双门接口，所以不变。通配符是"按方向开门"：`? extends Number`（读门开、写门焊死）、`? super Integer`（写门开、读按 Object）——相当于数组的协变去掉了 ArrayStoreException 版本，运行时检查被前移成编译错误（PECS 的由来）。

**问 6｜"桥接方法解决什么？'子类泛型重写擦除后签名可能不同，桥接方法维持多态调用关系'这个是啥？"**

先看问题怎么产生。泛型擦除后，父类方法签名变了：

```java
class Node<T> { public void set(T data) }              // 擦除后签名：set(Object)
class MyNode extends Node<Integer> {
    public void set(Integer data)                      // 子类覆写的签名：set(Integer)
}
```

擦除前它们是同一个方法（覆写成立）；擦除后**签名不同了**——`Node<Integer> n = new MyNode(); n.set(42);` 编译成 `invokevirtual Node.set(Object)`，运行时到 MyNode 里找 `set(Object)`，子类只有 `set(Integer)`，找不到 → **覆写关系断裂，多态失效**。

编译器的解法：在 MyNode 里自动生成一个**桥方法**（本机 JDK 25 实测）：

```
== MyNode 反射可见的方法 ==
  public void MyNode.set(java.lang.Integer)   isBridge=false
  public void MyNode.set(java.lang.Object)    isBridge=true    ← 编译器合成的桥

== 多态：父类引用调用 n.set(42) ==
  [MyNode.set(Integer)] data=42      ← 分派先进桥方法
  [Node.set(T)]         data=42      ← 桥转调真方法

== 反射按父类擦除签名调用 ==
  Node.class.getMethod("set", Object.class).invoke(n, 42) ✓ 也能走通
```

javap 反编译桥方法，就两步：`checkcast Integer` + `invokevirtual set(Integer)`——纯转调。

**桥方法的代价（AOP 的坑）**：子类里现在有两个 set——Spring AOP/CGLIB 拦截时可能把桥方法和真方法**都当切点**（同一调用进两次），且注解（@Transactional 等）标在真方法上、桥方法上没有，可能注解读取失败。框架的通用防御：`method.isBridge()` 过滤。

一句话：**桥方法 = 编译器为"泛型擦除导致覆写签名不一致"打的补丁——用擦除后的签名保住多态分派，方法体转调类型化的真方法。**

**问 7｜"桥接方法看下来是生成了一个同名方法，只是入参是 Object？还是有点不懂。"**

对一半，但"同名"这个词要小心：JVM 认方法靠**完整签名（方法名 + 参数类型）**，同名不同参就是两个完全独立的方法。准确说法是：编译器在子类里生成了一个**全新的独立方法** `set(Object)`，它和你写的 `set(Integer)` 毫无继承关系，唯一联系是方法体只有两步——强转，然后转调。

为什么非有它不可？先跑一个"假如编译器不补桥"的实验（手工模拟擦除后的世界，不用泛型，签名直接写死）：

```java
static class Node {
    public void set(Object o) { System.out.println("父类 set(Object) 执行了"); }
}
static class MyNode extends Node {
    public void set(Integer i) { System.out.println("子类 set(Integer) 执行了"); }
}
Node n = new MyNode();
n.set(42);
// 输出：父类 set(Object) 执行了   ← 你的覆写被完全绕过
```

不报错、不警告，程序安静地执行了父类代码。这就是没有桥方法的世界。

再看真实泛型编译后的字节码，三个关键位置：

```
== main 里的调用指令 ==
14: invokevirtual NodeG.set:(Ljava/lang/Object;)V     ← 编译期定死：按 set(Object) 发起调用

== MyNodeG 身上的桥方法（bridge=true）==
2: checkcast     Integer                              ← 第 1 步：参数强转
5: invokevirtual set:(Ljava/lang/Integer;)V           ← 第 2 步：转调你写的方法

== set(java.lang.Integer) ==                            ← 你亲手写的，正常编译
```

把桥方法翻译回 Java 源码，它就等价于这两行：

```java
public void set(Object o) {       // 编译器偷偷写的，源码里永远不出现
    Integer i = (Integer) o;
    this.set(i);
}
```

完整调用链：`g.set(42)` 按父类签名 `set(Object)` 发起 → 虚分派命中桥 → 桥强转后转调你写的 `set(Integer)`。桥不是你方法的副本，是挂在你方法上面的转发线。

**问 8｜"为啥要这么做？"**

直接动机：覆写关系断了，不补桥多态就废，编译器只剩两个选择——

- 承认"这不是覆写"：多态调用静默跑父类实现（上面的实验），泛型继承全部失效，没人能接受这个语义。
- 在子类补一个签名匹配的 `set(Object)`，方法体转调你的实现：语言层面"覆写成立"保住，兼容问题由编译器在暗处修掉。

编译器选了后者。在"签名必须精确匹配"这条 JVM 铁律下，这是唯一能保住多态的办法。

再往底层问：为什么要擦除，把签名搞断？因为 2004 年 Java 5 引入泛型时生态里已有海量存量代码，Java 选择让 `List<String>` 和 `List` 在运行期是**同一个类**——老 jar 包不重新编译就能和泛型代码混用，这就是擦除的全部目的：向后兼容。如果泛型信息运行期保留（C# 那样），父类方法本来就是 `set(Integer)`，覆写签名天然一致，桥方法根本不需要存在。

桥方法还是真实存在的执行路径，raw 类型实验能证明——同时能看到它的 checkcast 站运行期类型防线这班岗：

```java
NodeG raw = new MyNodeG();      // raw 类型：绕过编译期泛型检查（只给警告）
raw.set("我不是Integer");       // 编译能过，运行期拦截
// Exception in thread "main" java.lang.ClassCastException:
//   String cannot be cast to Integer
//   at MyNodeG.set(MyNodeG.java:5)   ← 栈轨迹指向的就是桥方法
//                                     （源码里不存在，行号落在类声明行上）
```

调用链：`raw.set(...)` 按 `set(Object)` 签名发起 → 命中桥 → `checkcast Integer` 拦下 String。呼应前面泛型那节说的"raw 类型是编译期的漏洞、运行期有兜底"——兜底动作的具体位置就是桥方法里的 checkcast。

四步链条：擦除（为向后兼容）→ 覆写签名断裂 → 不修则多态失效 → 补桥保多态，checkcast 顺带兜底类型安全。

**问 9｜"父类和子类包括方法你都写下呢？我要看 Java 原始代码。"**

源码就这三个文件，全部内容：

```java
// NodeG.java —— 父类
public class NodeG<T> {
    public void set(T t) {
        System.out.println("父类版本，参数=" + t);
    }
}

// MyNodeG.java —— 子类，继承时把 T 定成 Integer
public class MyNodeG extends NodeG<Integer> {
    @Override
    public void set(Integer i) {
        System.out.println("子类版本，参数=" + i);
    }
}

// Main.java —— 调用
public class Main {
    public static void main(String[] args) {
        NodeG<Integer> g = new MyNodeG();
        g.set(42);   // 打印：子类版本，参数=42
    }
}
```

源码里看不到桥方法——它只在 class 文件里，编译器生成，不归源码管。

**问 10｜"'覆写关系断裂'这个是为啥来的？"**

因为 JVM 判断覆写只有一条标准：**方法名和参数类型一模一样**。`set(Object)` 和 `set(Integer)` 参数不一样，就是两个不相干的方法（重载），不是覆写。

这条标准严到非泛型场景下手写会被直接拒绝：

```
$ javac OverrideCheck.java
OverrideCheck.java:6: 错误: 方法不会覆盖或实现超类型的方法
        @Override
        ^
```

那泛型版本为什么 `@Override` 能编译通过？因为存在两个裁判：

- **编译器（懂泛型）**：看到 `extends NodeG<Integer>`，T 已定为 Integer，你写的 `set(Integer)` 恰好匹配 `set(T)` 的形状——按泛型规则覆写成立，放行。
- **JVM（只认签名）**：class 文件里 T 已不存在，只剩 `set(Object)` 和 `set(Integer)` 两个签名，按"一模一样才算覆写"比对——不成立。

同一个 `@Override`，两个裁判给出相反判罚，而运行期说了算的是 JVM 那个。JVM 为什么这么死板？虚分派必须高效：运行期拿着签名直接查方法表，签名是它唯一认识的 key，差一个字都查不到。

**问 11｜"应该是叫重载和重写吧？怎么理解来得及？"**

对。区分只看一条：

- **重载（overload）**：方法名相同、**参数不同**。编译期按参数类型定死调哪个。
- **重写（override，覆盖）**：方法名相同、**参数完全相同**，子类替换父类实现。运行期按实际对象是谁来调。

口诀：**重载看参数，重写看对象**。

```java
class MyNode extends Node {
    public void set(Integer i) { }   // 参数不同 → 重载（两个独立方法）
    @Override
    public void set(Object o) { }    // 参数完全相同 → 重写（替换父类实现）
}
```

桥方法一句话就通了：**擦除把你以为的"重写"降级成了"重载"**——你写 `set(Integer)` 时自我感觉在重写，但擦除后名字同参数不同，正是重载的定义；重载不参与多态，所以调用落到父类实现。桥方法干的就是上面第二个方法的事：编译器替你补一个参数完全相同的重写。

面试串联答法：被问"重载和重写的区别"，答完定义补一句"泛型擦除会让子类的重写在字节码层面退化成重载，编译器生成桥方法把它补回来"——一题带出擦除和桥方法两个考点。

**问 12｜"还是有点懵，没看出来有啥问题。"**

因为你默认了"程序调用 set 时会聪明地找到该调的那个方法"。它不聪明。把调用拆成两步：

1. **编译期（定死）**：编译器只看声明类型 `NodeG`，擦除后它身上只有 `set(Object)`——所以 `g.set(42)` 生成的指令就是"调 set(Object)"，传 42 也一样，运行期改不了。
2. **运行期（按名字找人）**：JVM 拿着 `set(Object)` 这张单子去实际对象 `MyNodeG` 身上找。你写的是 `set(Integer)`，名字一样参数不同，不是同一个人；家里没有 `set(Object)`，JVM 上父类找，父类实现签收执行。

快递类比：调用指令是张快递单，收件人印死 `set(Object)`，JVM 只认单子上的名字。你家只有 `set(Integer)`，快递员不认，扭头上父类家投递了。

"看不出问题"是因为这套走法程序照常运行。来一个后果可见的（手工模拟无桥世界，计数器）：

```java
static class Counter {
    int count = 0;
    public void add(Object v) { count++; }        // 父类逻辑：计次数
}
static class MyCounter extends Counter {
    public void add(Integer v) { count += v; }    // 你的"覆写"：累加数值
}
Counter c = new MyCounter();
c.add(10);
c.add(20);
System.out.println("实际 count = " + c.count);
// 实际 count = 2    ← 父类的 count++ 跑了两次
// 你期待的 30（累加）从来没出现，且全程无报错
```

"覆写断裂"的全部含义就这一句：**多态调用时，你的重写代码永远轮不到执行，父类旧逻辑继续跑，业务结果安静地错**。

**问 13｜"类的定义和实现呢？"**

换个角度看：每个方法的**实现体挂在方法名下**，两个名字各挂各的实现——

```
MyCounter 对象身上实际挂着：
add(Object)    ← 继承来的，实现体是父类的 count++
add(Integer)   ← 自己定义的，实现体是你的 count += v
```

覆写本来应该干的事：把 `add(Object)` 名下那份父类实现**替换掉**。但替换有前提——你必须在子类里定义一个参数完全相同的 `add(Object)`，你的实现体才会挂到这个名字下面。你定义的是 `add(Integer)`，参数不同，另一个名字，你的 `count += v` 只挂在自己名字下面，`add(Object)` 名下纹丝没动，还是父类旧实现。调用按名字找人，找到的自然是旧实现。

**不是你的实现丢了，是你的实现挂错了名字下面，而调用是按名字找的。**

桥方法 = 编译器在子类定义里替你补一个 `add(Object)`，实现体是强转加转调——这一补，`add(Object)` 名下挂的才从"父类的 count++"变成"通往你的 count += v 的转发"。

**问 14｜"所以这个的学术名叫啥？"**

- 现象/机制：**桥方法（Bridge Method）**——JLS 和 JVM 规范的正式术语。JVM 给它打两个标志位：**ACC_BRIDGE** + **ACC_SYNTHETIC**（表示"源码中不存在、编译器合成"），合起来定义为"编译器为维持泛型多态而合成的转发方法"。反射里 `Method.isBridge()` 查询。
- 根因：**类型擦除（Type Erasure）**。

加分点：桥方法还有个同胞场景——**协变返回类型**（子类覆写时把返回类型改成更具体的子类型，Java 5 引入）也靠它实现，同一机制的两个用途。

面试答法：被问"泛型擦除带来什么问题"，答"擦除让覆写签名在字节码层面不一致，编译器生成桥方法（ACC_BRIDGE + ACC_SYNTHETIC）维持多态，方法体是强转加转调"——重载重写、擦除、反射三个考点全串起来。

## 09 · 动态代理：JDK 动态代理 vs CGLIB（延伸）

> 三段代码全部在本机 JDK 25 实测运行，输出为真实结果。

### 会话问答

**问 1｜"JDK 动态代理怎么写、怎么工作？"**

```java
interface UserService {
    String getUser(int id);
    void save(String name);
}

UserService proxy = (UserService) Proxy.newProxyInstance(
    JdkProxyDemo.class.getClassLoader(),
    new Class<?>[]{ UserService.class },            // 要代理的接口
    (p, method, mArgs) -> {                          // InvocationHandler：所有方法的统一入口
        System.out.println("[前置] " + method.getName());
        Object r = method.invoke(target, mArgs);     // 反射调真实对象
        System.out.println("[后置]");
        return r;
    });

System.out.println(proxy.getClass());   // class $Proxy0 —— 运行时生成的类
proxy.getUser(7);
```

实测输出：

```
代理对象的类: class $Proxy0
它实现的接口: [interface UserService]
    [前置] getUser[7]
    [后置] 已返回: user-7
调用 getUser(7) → user-7
```

工作机制：`newProxyInstance` **运行时生成字节码并 defineClass**，产出一个 `$Proxy0 extends Proxy implements UserService` 的类——它的每个方法都只有一行：转发给 InvocationHandler.invoke。增强逻辑（日志/事务/权限）全写在 handler 里。**硬约束：只能代理接口**——$Proxy0 已经继承了 Proxy，Java 单继承，没法再继承目标类。

**问 2｜"CGLIB 呢？"**

CGLIB 走另一条路：**生成目标类的子类**（字节码增强），不需要接口：

```java
class UserService {                        // 没有任何接口
    public String getUser(int id) { return "user-" + id; }
    public final String version() { return "1.0"; }     // 故意演示边界
}

Enhancer enhancer = new Enhancer();
enhancer.setSuperclass(UserService.class);             // 生成"子类"
enhancer.setCallback((MethodInterceptor) (obj, method, mArgs, proxy) -> {
    System.out.println("[前置] " + method.getName());
    Object r = proxy.invokeSuper(obj, mArgs);           // 调父类原方法
    System.out.println("[后置]");
    return r;
});
UserService proxy = (UserService) enhancer.create();
```

实测输出（cglib 3.3.0 + JDK 25 + `--add-opens java.base/java.lang=ALL-UNNAMED`）：

```
代理对象的类: UserService$$EnhancerByCGLIB$$a10dad56    ← 生成的是子类
它是 UserService 的子类吗: true
    [前置] getUser
    [真实对象] getUser(7)
    [后置]
调用 getUser(7) → user-7
    [真实对象] version() —— final 方法                  ← 没有前置/后置！
调用 version() → 1.0
```

注意 version()：**final 方法无法被子类覆写**，调用直接穿透到原方法，拦截器完全没参与——这是 CGLIB 的能力边界（final 方法、private 方法、final 类都代理不了，且是静默穿透，增强丢失不报错）。

另一个实测踩到的现实问题：cglib 3.3.0 在 JDK 25 上抛 `InaccessibleObjectException`——它用反射调 `ClassLoader.defineClass`，被 JDK 16+ 的模块强封装挡住，必须加 `--add-opens`。Spring 6 的解法是把 cglib 内嵌进 spring-core 自己维护，改用 `Lookup.defineClass` 等新机制。

**问 3｜"两者区别与选型？"**

| | JDK 动态代理 | CGLIB |
|---|---|---|
| 前提 | 目标必须实现**接口** | 目标是**类**即可（不能是 final 类） |
| 机制 | 运行时生成接口实现类 $Proxy0 | 运行时生成目标类的**子类**（字节码增强） |
| 统一入口 | InvocationHandler.invoke | MethodInterceptor.intercept |
| 不能代理 | 没有接口的类 | final 方法 / private 方法 / final 类 |
| 依赖 | JDK 内置（reflect.Proxy） | 第三方库（Spring 内嵌重写版） |
| 性能 | 反射调用（JDK 有优化） | 生成方法体直调 + FastClass 避免反射 |

Spring 的选择：目标有接口默认 JDK 代理，`proxyTargetClass=true` 或无接口时用 CGLIB（Spring Boot 2.x 起 AOP 默认 CGLIB）。**坑**：CGLIB 代理 final 方法会静默穿透（增强丢失不报错）；桥方法会让 AOP 对同一调用双重拦截（见第 08 章问 6）。

## 10 · 序列化的本质：对象图 vs DTO，以及 RMI（延伸）

### 会话问答

**问 1｜"序列化是啥？transient 在哪一步进行过滤的？"**

序列化 = 把内存里的对象变成一串字节（存文件/走网络）；反序列化 = 字节流还原成对象。Java 三行：类实现 `Serializable`（标记接口，无方法）→ `ObjectOutputStream.writeObject(obj)` 写出 → `ObjectInputStream.readObject()` 读回。本机实测（JDK 25）：

```java
static class Person implements Serializable {
    String name;                   // 进流
    int age;                       // 进流
    transient int cache = 99;      // 被过滤
    static String country = "CN";  // 永远不进流（属于类不属于对象）
}
```

序列化产物是 82 字节的二进制文件，解码开头：

```
aced 0005                     魔数 + 版本号
73 72                         TC_OBJECT + TC_CLASSDESC：一个对象 + 类描述符
"SerDemo$Person"              类名
<serialVersionUID>            版本号
02 00 02                      标志 + 【字段数 = 2】★
49 0003 "age"                 字段表：int 类型，名叫 age
4c 0004 "name" String         字段表：对象类型，名叫 name
... 之后才是数据：name="张三"、age=18
```

**transient 的过滤发生在"构建类元数据（ObjectStreamClass）"这一步**：序列化一个类的第一件事是反射遍历它的字段、把 transient 和 static 剔除、剩下的组成字段表并缓存。之后写数据按字段表来——transient 字段连"被跳过"的机会都没有，它根本不在名单上。读回验证：cache=0（int 默认值，transient 字段反序列化后不恢复）；static 同理（属于类不属于对象）。

**问 2｜"transient 只是标记？COW 的 writeObject/readObject 是怎么处理这个字段的？"**

transient = 默认序列化机制（defaultWriteObject/defaultReadObject）的**排除名单**；它和手写的 writeObject/readObject 是配合关系——transient 圈出"默认机制不许碰、我手写接管"的地盘。反事实：array 不标 transient，defaultWriteObject 会把整个数组（含容量空洞）先写进流，手写部分再写一遍 → 流里两份数据，脏且膨胀。

COW 的处理（:1007/:1028）：

```java
private void writeObject(java.io.ObjectOutputStream s) {
    s.defaultWriteObject();              // 字段表为空 → 实际啥也不写
    Object[] es = getArray();            // 一次 volatile 读 = 不可变快照
    s.writeInt(es.length);
    for (Object e : es) s.writeObject(e);
}                                        // ★ 全程没加锁：并发写换新数组，不影响快照
                                         //   对照 ArrayList 要 expectedModCount 对账

private void readObject(java.io.ObjectInputStream s) {
    s.defaultReadObject();
    resetLock();                         // ★ bind to new lock —— 见问 3
    int len = s.readInt();
    Object[] es = new Object[len];
    for (int i = 0; i < len; i++) es[i] = s.readObject();
    setArray(es);                        // 重建 + volatile 发布
}
```

**问 3｜"transient final 的 lock 反序列化后是啥？resetLock 是干嘛的？"**

大坑现场：**反序列化不运行构造器和字段初始化器**——`final transient Object lock = new Object()` 的初始化器在 <init> 里，不跑 → lock 反序列化后是 **null**。不处理的话，反序列化出的列表第一次写操作就 NPE。

JDK 25 的解法（:2097）：readObject 里调 resetLock()，内部用 **Unsafe.putReference 强行给 final 字段重新赋值**（JDK 内部类的特权；业务代码的 Unsafe 写 final 受限）：

```java
private void resetLock() {
    final Unsafe U = Unsafe.getUnsafe();
    U.putReference(this,
        U.objectFieldOffset(CopyOnWriteArrayList.class, "lock"),
        new Object());
}
```

业务代码踩这个坑的解法：字段去掉 final 在 readObject 里重建，或用 readResolve 重建整个对象。对照 ArrayList 的 writeObject：它需要 expectedModCount 对账（序列化中途被并发修改会 CME）——Q17 的知识直接复用。

**问 4｜"为啥不表示成一个 JSON 的字符串？也算是序列化，还不用这么麻烦。"**

你的判断在今天是对的——业界默认 JSON/Protobuf，Java 原生序列化公认是设计失误（安全漏洞重灾区）。但两者有一个根本差异：**序列化的对象不同**。

- Java 原生序列化：**对象图**。引用关系保真（handle 机制：同一对象第二次出现只写引用号），类型完整，循环引用可处理。
- JSON：**数据**。对象图拍平成树，同一对象出现两次写两份，反序列化是两个新对象，引用关系丢失。

本机 demo 验证：Team 里 leader 字段和 members[0] 指向同一个 Person → 序列化往返后 `leader == members[0]` 为 **true**，改 members[0].age，leader.age 跟着变（同一对象）；流里第二次出现"张三"只写了 `71 007e0006`（TC_REFERENCE + 句柄号 6），不是再写一遍对象。

| | Java 原生序列化 | JSON |
|---|---|---|
| 序列化内容 | 对象图（引用保留） | 数据（拍平） |
| 类型信息 | 完整，直接得原类型 | 无类型，靠约定/注解 |
| 跨语言 | ❌ 只有 JVM | ✅ 任何语言 |
| 体积 | 二进制小 | 文本大（Protobuf 更小更快） |
| 安全 | 重灾区（反序列化 RCE） | 相对安全 |

**问 5｜"RMI 为啥要对象引用？对象引用咋表示？大概是什么样子？"**

RMI（Remote Method Invocation，JDK 1.1，1997）的愿景：**在 A 机器的代码里调用 B 机器上对象的方法，写法和本地调用一样**：

```java
// 服务端
public interface Hello extends Remote {
    String sayHi(String name) throws RemoteException;
}
public class HelloImpl extends UnicastRemoteObject implements Hello {
    public String sayHi(String name) { return "Hi, " + name; }
    public static void main(String[] a) throws Exception {
        LocateRegistry.createRegistry(1099).rebind("hello", new HelloImpl());
    }
}
// 客户端
Hello h = (Hello) Naming.lookup("rmi://B机器:1099/hello");
h.sayHi("张三");                          // 写法是本地调用，实际走网络
```

客户端手里的 h 是 **stub（桩）**——不是真实对象，是"主机+端口+对象ID"打包成的远程引用代理；调用时 stub 序列化方法名和参数发到服务端，服务端调用真实对象，结果序列化传回。

"对象引用"在 RMI 语境有两层（别混）：**序列化流里的 handle**——复杂参数对象图传过去不变形（同一对象只存一份，demo 里的 TC_REFERENCE）；**stub 远程引用**——远端对象的代理，本身可序列化（内容=定位信息）。

RMI 的赌注"网络调用伪装成本地调用"后来被证伪（Waldo 1994 经典论文：本地和远程的失败模式、延迟、内存语义本质不同，伪装是错的）。业界转向显式传 DTO：Dubbo/gRPC/REST——接口+代理的结构和 RMI 一脉相承，但传的是数据。RMI 现在只剩 EJB 时代遗留系统在用，新项目别用；Java 原生序列化的安全红线也因此写成：**永远不用它接收不可信数据**。

## 11 · 红黑树与 408 真题（Q19）【P1】

### 手册原文（解释版）

**① 阈值必须和实际分支一起解释。** JDK 8 有树化阈值 8、最小树化容量 64，但普通 put 的链表追加路径，常在加入第九个节点时进入 treeifyBin 判断；不能把常量名直接读成"第八个节点必变树"。即使到了该路径，数组容量小于 64 时也优先扩容，因为碰撞可能只是桶太少，扩容比维护树更合适。

**② 红黑树如何限制高度。** 红黑树以颜色、红节点不能有红孩子、各到叶端路径黑节点数一致等约束，避免树退化成一条链。修复使用重新染色和局部旋转。左旋小树：原来 10 的右孩子是 20，20 的左孩子是 15；左旋 10 后，20 接替 10 的父链接，10 成为 20 的左孩子，15 从 20 的左边转到 10 的右边。中序仍是 10、15、20，键的有序关系未变。右旋正好反向。

**③ 树化不代表永不退化或绝对对数查找。** 扩容把树桶分成两侧时，节点较少的一侧可退回链表；删除还可能根据结构判断退化。面对散列相同又无法建立有效可比较顺序的键，查找可能探索两侧分支，不能无条件承诺每次严格 O(log n)。

### 会话问答

**问 1｜"到 8 个节点就树化吗？——就是既要看节点个数，也要看总数？"**

对，两个条件缺一不可。**条件一：桶内第 9 个节点插入时触发判断**——往有 m 个节点的桶插入时 binCount = m−1，判断 `m−1 >= 7` 即 m ≥ 8，所以"满 8 就树化"是误读，实际是"已有 8 个、插入第 9 个时"。**条件二：表容量 ≥ 64**（MIN_TREEIFY_CAPACITY），否则 treeifyBin 转成 resize()——小表长链大概率是桶太少，扩容摊开元素治本，树化只治标。对称阈值：退化 ≤ 6（UNTREEIFY_THRESHOLD），8/6 隔离带防抖动。8 来自泊松分布：负载 0.75 下每桶平均 0.5 个，P(8) ≈ 6×10⁻⁸——树是坏 hash 的保险丝，不是常态；TreeNode 内存约普通 Node 的 2 倍。

**问 2｜"按 408 的考试难度和要求讲解红黑树。"**

408 只考选择题。范围与要点：

**五性质**：①每结点非红即黑 ②根黑 ③叶结点（**外部结点 nil**——最大陷阱）是黑 ④红结点的孩子必黑（无连续红）⑤任一结点到所有后代叶的路径黑结点数相同（黑高 bh）。

**可推导结论**：最长路 ≤ 2×最短路；n 个内部结点 h ≤ 2log₂(n+1)；红结点 ≤ n/2。推导核心：黑高 k 的树至少 2^k − 1 个结点（根必黑 → 两棵子树黑高都是 k−1 → 归纳；全黑满树取到下界）。常见猜想"黑高 k 的最少结点是（k−1 层满树）+1"错在：**加红不涨黑高**（加了还是 k−1），**加黑必须每条路径都加**（性质 5 是对所有路径的要求）——恰好就是全黑满树。验证：bh=2 最少 3 结点（根+两黑孩子），2 个结点的树黑高只有 1。

**插入四型**（新结点一律染红，只可能违反"无连续红"）：父黑→完；父红看叔叔——**叔红：变色上溯（0 旋转）；叔黑：LL/RR 单旋（父黑祖红）或 LR/RL 双旋（z 黑父祖红）**，最多 2 次旋转。不对称的染色是选择题最爱。

**删除双黑框架**（最多 3 次旋转）：删红结点直接结束；删黑结点产生双黑——兄弟红（旋 1 次转成兄弟黑）、红侄（旋 1~2 次结束）、双黑侄（兄弟变红、双黑上移，0 旋转）、到根结束。

**AVL 对比**：AVL 严格平衡（|bf|≤1）查找略快、维护贵；红黑树松平衡（最长 ≤ 2×最短）换"删除最多 3 次旋转"——增删频繁场景的工程选择。

**问 3｜"旋转的目的是啥？我看旋转后的黑高也不一样啊。"**

修复前后黑高**一分不变**——变的只是"黑结点由谁扮演"（G 的黑挪给了 P/z）。"黑高不一样"的错觉来自图里把叔叔 u 画成叶子——u 是子树根，它内部每条路径的黑数与 β 子树相同（修复前性质 5 保证），把 u 展开数，每条路径严格相等。旋转的两个不变量：**中序不变**（BST 保住）+ **黑高不变**；旋转的目的 = 在这两个约束下重摆结构，让"连续红"变成可分离的形状。对比：AVL 旋转是为了降高度；红黑树旋转是在黑高不动的前提下消除颜色违规。

**问 4｜"红黑树和 AVL 的考研真题罗列一下。"（含"你从网上搜啊"的考证过程）**

考证方法：逐年抓取 csgraduates.com 的 408 真题页（2022–2026 的数据结构选择题 1–11 清单 + 2026 大题），此前凭记忆的回答里"2022 年考过一道红黑树"是**搜索摘要的幻觉**，抓原题页后推翻。

### 与其他题的连线

Q18：树化桶的 lo/hi 拆分与 HashMap 扩容同源，某侧 ≤6 退回链表。Q21：CHM 的 TreeBin 是红黑树的并发包装（读侧有类似读锁的协调）。Q19 的"树化几乎不发生"（泊松）与 Q17 的"fail-fast 尽力而为"：JDK 在非常用路径上普遍选择"便宜 + 兜底"而不是"昂贵 + 精确"。
