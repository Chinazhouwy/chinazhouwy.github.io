# 第228题：保险销售领域建模与系统边界（简历专项 02）

## 题目
保险销售、电商、业务员、客户和出单链路如何拆分领域与系统边界？核心业务对象和状态如何建模？

## 用户原始回答
> 出单和领域边界无非就是对象有哪些信息属性、可能牵扯哪些变化。边界就是哪些信息不是本系统页面录入的。像出单，产品要从产品工厂取，我们负责产品订单的流转、支付状态的变更。但支付信息通知是支付那边负责的，我们更多是协调状态流转和用户购买行为的控制。感觉有点难说清楚。

## 评分与扣分点

**评分：4/10**

- 答对了核心方向："我们负责状态流转，产品从产品工厂取，支付结果从支付网关收"
- 提出了"边界 = 非本系统录入的信息"这一直观理解
- 但缺少结构化的领域划分描述
- 没有展开核心业务对象的建模（投保单、保单、商机、支付流水）
- 缺少状态机设计的防非法流转讨论

## 完整答案

### 领域拆分（限界上下文）

```
产品工厂（外部）          支付网关（外部）           用户中心（外部）
  │ 产品定义/费率            │ 支付/退款通知            │ 客户基本信息
  │ 险种/条款/规则            │ 资金流水                 │ 实名认证
  ▼                         ▼                         ▼
┌─────────────────────────────────────────────────┐
│              保险销售中台（核心域）                  │
│                                                   │
│  投保单 ──→ 核保 ──→ 保单 ──→ 续期/批改/退保        │
│   │                                                    │
│   └── 商机 ──→ 跟进 ──→ 转化 ──→ 业绩                 │
│                                                    │
│  核心职责：状态流转、业务规则校验、行为控制               │
└─────────────────────────────────────────────────┘
```

### 核心业务对象和状态建模

| 对象 | 核心属性 | 关键状态流转 |
|------|---------|------------|
| 投保单 | 产品ID、投保人、被保人、保额、保费 | 草稿→待支付→已支付→核保中→已承保/拒保 |
| 保单 | 保单号、险种、生效日、到期日 | 有效→停效→复效→期满/退保 |
| 商机 | 客户ID、来源渠道、产品意向、业务员 | 新建→分配→跟进中→已转化/已关闭 |
| 支付流水 | 关联投保单号、金额、渠道 | 待支付→支付中→已到账/已退款（来自支付回调） |

### 状态机防非法流转

- 不能从"草稿"直接跳到"已承保"
- 不能从"已退保"再回到"有效"
- 支付回调到达后才校验业务规则，通过后才扭转状态
- 主数据不落地，只落地流转轨迹

## 面试回答模板

> 保险销售中台的核心职责不是制造数据，而是编排状态流转和守护业务规则。产品、支付、用户都是外部协作域，我们通过回调、接口和事件跟它们协作，主数据不落地，只落地流转轨迹。比如投保单从"待支付"到"已承保"，不是收到钱就改状态，而是支付回调确认到账后，再做规则校验——险种在售、年龄合规、健康告知通过——全部通过才扭转。
